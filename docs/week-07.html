1. Connection · Session · Transaction

1-1. 연결 두 개를 구별하기

각자의 FastAPI는 Supabase의 Pooler에 접속합니다. Pooler는 실제 PostgreSQL 연결을 관리하는 중간 서버입니다. “내 프로그램과 Pooler의 연결”과 “Pooler가 배정하는 PostgreSQL 연결”은 서로 다른 구간입니다.

구간누가 여는가역할
팀원 FastAPI ↔ Poolerpsycopg.connect()클라이언트 요청 전달
Pooler ↔ PostgreSQLPooler실제 SQL 실행을 위한 DB 연결 배정

DB session은 연결에 딸린 상태와 문맥입니다. 사용자 로그인 session이나 브라우저 cookie와는 다른 개념입니다. Transaction은 하나의 성공/실패 단위입니다. COMMIT은 확정, ROLLBACK은 취소이며, 둘 다 연결 종료와 같은 말이 아닙니다.

1-2. Pooler가 실제 DB 연결을 언제 돌려받는가

시점Session mode · 5432Transaction mode · 6543
첫 transaction연결 A에서 실행배정받은 연결 A에서 실행
COMMIT 후 대기클라이언트 연결이 살아 있으면 A 유지A를 반환해 다른 클라이언트가 사용 가능
다음 transaction같은 A에서 실행A 또는 다른 B에서 실행
연결 종료A 반환클라이언트 연결 종료

Transaction mode라고 SQL 한 문장만 실행할 수 있는 것은 아닙니다. 하나의 transaction 안에서 여러 SQL을 실행할 수 있습니다. 다만 transaction 사이에 같은 DB session이 유지된다고 가정할 수 없습니다. Session mode는 이런 제약이 적어 이번 기초 실습의 기본으로 선택합니다. 포트 숫자는 여기의 Supabase shared pooler 기준이지 모든 DB 서비스의 공통 규칙은 아닙니다.

Transaction mode로 전환할 때는 session에 의존하는 기능을 점검하고 Psycopg의 자동 prepared statement를 prepare_threshold=None으로 끕니다. 이는 반복 SQL의 session 내 준비 기능을 끄는 것이며, %s parameter binding은 그대로 사용합니다.

1-3. 오늘 코드의 실제 수명

with get_connection() as conn:
    row = conn.execute(
        "SELECT id, name, email FROM public.users WHERE id = %s",
        (user_id,),
    ).fetchone()
# 정상 종료: COMMIT + CLOSE
# 예외 종료: ROLLBACK + CLOSE
  1. get_connection(): 연결을 엽니다.
  2. 첫 SQL: Psycopg 기본 설정에서 transaction이 시작됩니다. SELECT도 해당합니다.
  3. 블록 정상 종료: commit 후 연결을 닫습니다.
  4. 블록에서 예외 발생: rollback 후 연결을 닫고 예외를 밖으로 전달합니다.

Session mode여도 이 코드는 서버가 켜져 있는 내내 연결을 유지하지 않습니다. 요청마다 연결을 열고 닫습니다. 따라서 현재처럼 transaction 하나만 실행하는 짧은 요청에서는 두 모드의 점유 시간 차이가 작습니다. Python 쪽 connection pool을 추가하는 것은 이후 최적화 주제입니다.

이해 확인: commit하면 연결도 닫히나요?

아니요. conn.commit() 자체는 연결을 닫지 않습니다. 이번 코드에서는 connection context manager가 블록을 종료하면서 commit과 close를 모두 수행하기 때문에 함께 일어납니다.

2. 팀장 사전 준비: 같은 Supabase에 접속하기

이 절은 팀장이 수업 전에 완료합니다. 실제 서비스 데이터가 없는 학습 전용 프로젝트를 사용합니다. 학생들은 Supabase Dashboard 계정을 공유하거나 새 프로젝트를 만들 필요가 없습니다. 각자 FastAPI를 실행하고 팀장이 전달한 DB 계정으로 같은 프로젝트에 접속합니다.

팀장은 6주차 schema의 public.users(id, name, email, password_hash)와 dummy data를 준비합니다. email에는 UNIQUE, id에는 identity가 있어야 합니다. 이미 준비된 DB에서 CREATE TABLE이나 seed를 반복할 필요는 없습니다.

2-1. 학생 계정에 실습 권한 주기

관리자 postgres 비밀번호는 팀장만 사용합니다. 아래 SQL은 학생 5명용 study01~study05 계정과 권한을 묶는 study_members role을 만듭니다. 계정은 비밀번호를 설정하기 전까지 password 인증으로 로그인할 수 없습니다. 기존 계정의 비밀번호나 추가 권한은 변경하지 않으므로 이 이름들은 이번 실습 전용으로 사용하세요.

팀장용 SQL — SQL Editor에서 실행
-- Leader only, in a dedicated study project. Requires public.users from Week 06.
-- Does not create or reset users. No passwords are embedded in this script.
BEGIN;
DO $roles$
DECLARE role_name text;
BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'study_members') THEN
        CREATE ROLE study_members NOLOGIN;
    END IF;
    FOREACH role_name IN ARRAY ARRAY['study01','study02','study03','study04','study05']
    LOOP
        IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = role_name) THEN
            EXECUTE format(
                'CREATE ROLE %I LOGIN INHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS',
                role_name
            );
        END IF;
        EXECUTE format('GRANT study_members TO %I', role_name);
    END LOOP;
END
$roles$;

GRANT CONNECT ON DATABASE postgres TO study_members;
GRANT USAGE ON SCHEMA public TO study_members;
GRANT SELECT (id, name, email) ON public.users TO study_members;
GRANT INSERT (name, email, password_hash) ON public.users TO study_members;
GRANT UPDATE (name) ON public.users TO study_members;
GRANT DELETE ON public.users TO study_members;
GRANT USAGE ON SEQUENCE public.users_id_seq TO study_members;

ALTER TABLE public.users ENABLE ROW LEVEL SECURITY;
DROP POLICY IF EXISTS study_members_crud ON public.users;
CREATE POLICY study_members_crud ON public.users
    FOR ALL TO study_members USING (true) WITH CHECK (true);
COMMIT;

-- Next, assign a different password to each new LOGIN role with psql \password.
-- The policy allows all study rows; it is not per-user ownership enforcement.

GRANT는 어떤 작업/column을 사용할지, RLS policy는 어떤 row에 접근할지를 결정합니다. 학생들은 id·name·email을 읽고, 사용자를 생성하고, name을 수정하고, 삭제할 수 있습니다. password_hash 조회 권한은 주지 않습니다. 따라서 학생 계정의 SELECT * FROM users는 실패하는 것이 정상입니다.

이 policy는 실습 테이블 전체 row를 허용합니다. 학생별 소유권을 강제하는 인증 설계는 아닙니다. 각자 자기 email과 id만 수정·삭제하기로 약속합니다. 이후 인증 수업에서 소유권 검증을 다룹니다. 기존 anon/authenticated 접근 설정은 이 SQL에서 넓히지 않습니다.

2-2. 비밀번호는 명령 입력 기록에 남기지 않기

팀장의 터미널에서 psql로 접속합니다. HOST와 PROJECT_REF는 실제 Connect 창의 값으로 바꿉니다. -W가 팀장의 DB 비밀번호를 물으며 입력 내용은 화면에 표시되지 않습니다. psql이 없다면 6주차 PostgreSQL 설치 안내의 client를 사용합니다.

PGSSLMODE=require psql -h YOUR_POOLER_HOST -p 5432 \
  -U postgres.YOUR_PROJECT_REF -d postgres -W

접속 후 다음 명령을 한 줄씩 실행합니다. 각 계정에 서로 다른 비밀번호를 정하고 해당 팀원에게 개인적으로 전달합니다. 아래는 SQL이 아니라 psql 전용 명령입니다. Dashboard SQL Editor에 넣지 않습니다.

\password study01
\password study02
\password study03
\password study04
\password study05
\q

팀장은 직접 study01로 연결해 조회 한 번을 확인한 다음 나머지 팀원에게 배포합니다. 수업 후에도 사용할 계정은 유지하고, 더 이상 참여하지 않는 계정은 팀장이 접근을 회수합니다.

공통 정보학생마다 다른 정보

예: study01은 study01.w07.001@example.com, study02는 study02.w07.001@example.com을 사용합니다. 두 번째 실습 때는 002로 바꿉니다. DB 계정 이름과 users 테이블의 사용자 데이터는 다른 개념입니다. 같은 DB에 연결되어 있으므로 다른 사람이 commit한 데이터도 이후 조회에서 보일 수 있습니다. row 개수나 id가 나만의 실습 순서대로 늘어난다고 가정하지 않습니다.

3. 전원 연결 확인: 여기까지 함께 통과합니다

3-1. 6주차 코드와 환경 확인

팀장이 공유한 6주차 완료 코드가 있어야 합니다. 아래 명령은 pyproject.toml이 있는 프로젝트 루트에서 실행합니다. 개인 수정이 있다면 먼저 보존하고, 수업 시작 직전에 무작정 reset하지 않습니다.

uv sync
uv add email-validator

EmailStr 검증에 사용할 의존성을 명시적으로 추가합니다. uv add는 pyproject.toml과 uv.lock을 갱신합니다. 이미 팀장이 반영한 최신 lockfile을 받았다면 uv sync로 충분합니다.

3-2. 바뀐 Connect 화면에서 값 찾기

팀장: 프로젝트 상단 Connect → Direct / Connection string → Session pooler → View parameters를 확인합니다. 화면 배치가 다르면 Session pooler 연결 문자열의 host·port·database를 확인합니다. UI의 Direct 탭과 연결 방식의 Direct connection은 같은 선택이 아닙니다. 이번 방식은 Session pooler입니다.

학생: 받은 값으로 프로젝트 루트에 .env.local을 만듭니다. 파일명 맨 앞의 점을 포함합니다. .env.example은 예시일 뿐이며 프로그램은 .env.local을 읽습니다.

PGHOST="YOUR_SESSION_POOLER_HOST"
PGPORT=5432
PGDATABASE=postgres
PGUSER="study01.YOUR_PROJECT_REF"
PGPASSWORD="YOUR_STUDENT_ROLE_PASSWORD"

shared pooler에서 custom DB role의 user는 study01.PROJECT_REF 형식입니다. 학생에게 보이는 postgres용 문자열을 그대로 쓰지 않습니다. 비밀번호는 자기 study01 계정의 비밀번호이며 Supabase 로그인 비밀번호나 API key가 아닙니다. 별도 PG 변수에 넣으므로 비밀번호를 URL 인코딩하지 않습니다. 공백·# 등이 포함되면 따옴표로 감쌉니다.

.gitignore에는 .env, .env.*와 예외 !.env.example이 있어야 합니다. 다음 명령이 .env.local을 출력하면 Git ignore가 적용된 것입니다. 비밀번호를 화면 공유하거나 Git에 올리지 않습니다.

git check-ignore .env.local

3-3. 연결 함수: 6주차 코드 그대로 사용

app/database.py 전체 코드 확인
import os
from pathlib import Path

import psycopg
from dotenv import load_dotenv
from psycopg.rows import dict_row

load_dotenv(Path(__file__).resolve().parents[1] / ".env.local")


def get_connection():
    required = ("PGHOST", "PGDATABASE", "PGUSER", "PGPASSWORD")
    missing = [name for name in required if not os.getenv(name)]
    if missing:
        raise RuntimeError(f"Set these variables in .env.local: {', '.join(missing)}")
    return psycopg.connect(
        host=os.environ["PGHOST"],
        port=int(os.getenv("PGPORT", "5432")),
        dbname=os.environ["PGDATABASE"],
        user=os.environ["PGUSER"],
        password=os.environ["PGPASSWORD"],
        sslmode="require",
        connect_timeout=5,
        row_factory=dict_row,
    )

기존 환경 변수가 있으면 load_dotenv 기본 동작상 파일보다 우선합니다. .env.local을 고쳤는데도 같은 오류가 나면 실행 중인 서버를 종료하고, 터미널에 설정된 PG 변수를 확인합니다. sslmode=require는 암호화를 요구합니다. 배포 수준의 인증서 검증에는 CA 설정과 verify-full이 필요하며 이번 로컬 수업에서는 설정을 단순하게 유지합니다.

4. API 계약과 Validation

Endpoint입력성공실패
GET /userslimit 1~100, 기본 20200, items 배열422
GET /users/{id}정수 id200, 사용자404 / 422
POST /usersname, email 필수201, 생성된 사용자422 / 중복 409
PATCH /users/{id}name 필수200, 수정된 사용자404 / 422
DELETE /users/{id}정수 id204, body 없음404 / 422

이번 PATCH의 계약은 이름 변경만 허용입니다. 사용자 전체 중 name만 바꾸므로 partial update이며, body에서 name 자체를 생략할 수 있다는 뜻은 아닙니다. 빈 객체 {}, null, email 변경 요청은 모두 422로 거부합니다. 여러 optional 필드를 받는 일반 PATCH는 확장 과제로 남깁니다.

  • name: 앞뒤 공백 제거 후 1~50자. 공백만 있으면 거부.
  • email: EmailStr로 형식 검증 후 전체 소문자 저장. 소문자 정책은 이번 수업에서 정한 계약이며 모든 서비스의 보편 규칙은 아닙니다.
  • 예상하지 않은 입력 필드는 거부합니다. 클라이언트가 id나 password_hash를 지정하지 않습니다.
  • 출력에는 id, name, email만 포함합니다.

API 검증은 사용자에게 빠른 피드백을 주고 DB 제약은 최종 데이터 무결성을 지킵니다. email을 SELECT로 먼저 확인하는 것만으로 동시 요청의 중복을 막을 수는 없습니다. 두 요청이 동시에 “없음”을 확인할 수 있으므로 DB UNIQUE 제약을 유지하고 INSERT 실패를 처리합니다.

5. main.py에서 CRUD 완성하기

CRUD는 데이터 생성(Create), 조회(Read), 수정(Update), 삭제(Delete)를 뜻합니다. 7주차에는 입력·출력 정의, HTTP 처리, SQL을 모두 app/main.py에 작성합니다. database.py의 연결 함수는 유지합니다. 8주차에 같은 코드를 역할별 파일로 옮깁니다.

먼저 기존 GET 두 개를 확인합니다. 그다음 UserCreate와 POST를 추가합니다. POST로 받은 id로 GET을 실행합니다. 다음으로 UserNamePatch와 PATCH를 추가합니다. 마지막에 DELETE를 추가합니다. 아래 코드는 단계별로 비교할 완성본입니다.

app/main.py 전체 완성 코드
from typing import Annotated

from fastapi import FastAPI, HTTPException, Query, Response
from psycopg.errors import UniqueViolation
from pydantic import BaseModel, ConfigDict, EmailStr, StringConstraints, field_validator

from app.database import get_connection

UserName = Annotated[str, StringConstraints(strip_whitespace=True, min_length=1, max_length=50)]


class UserCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")
    name: UserName
    email: EmailStr

    @field_validator("email")
    @classmethod
    def normalize_email(cls, value: str) -> str:
        return value.lower()


class UserNamePatch(BaseModel):
    model_config = ConfigDict(extra="forbid")
    name: UserName


class UserResponse(BaseModel):
    id: int
    name: str
    email: str


class UserListResponse(BaseModel):
    items: list[UserResponse]


app = FastAPI(title="LikeLion Backend Study")


@app.get("/", tags=["root"])
def read_root() -> dict[str, str]:
    return {"message": "Hello World"}


@app.get("/health", tags=["health"])
async def health() -> dict[str, str]:
    return {"status": "ok", "project_name": "2026 Fall Backend"}


@app.get("/users", tags=["users"], response_model=UserListResponse)
def list_users(limit: int = Query(default=20, ge=1, le=100)):
    with get_connection() as conn:
        users = conn.execute(
            "SELECT id, name, email FROM public.users ORDER BY id LIMIT %s", (limit,)
        ).fetchall()
    return {"items": users}


@app.get("/users/{user_id}", tags=["users"], response_model=UserResponse)
def read_user(user_id: int):
    with get_connection() as conn:
        user = conn.execute(
            "SELECT id, name, email FROM public.users WHERE id = %s", (user_id,)
        ).fetchone()
    if user is None:
        raise HTTPException(status_code=404, detail="User not found")
    return user


@app.post("/users", tags=["users"], status_code=201, response_model=UserResponse)
def create_user(body: UserCreate):
    try:
        with get_connection() as conn:
            user = conn.execute(
                """INSERT INTO public.users (name, email, password_hash)
                   VALUES (%s, %s, %s) RETURNING id, name, email""",
                (body.name, str(body.email), "!dummy-no-login"),
            ).fetchone()
        return user
    except UniqueViolation as exc:
        if exc.diag.constraint_name != "users_email_key":
            raise
        raise HTTPException(status_code=409, detail="Email already exists") from exc


@app.patch("/users/{user_id}", tags=["users"], response_model=UserResponse)
def update_user(user_id: int, body: UserNamePatch):
    with get_connection() as conn:
        user = conn.execute(
            """UPDATE public.users SET name = %s WHERE id = %s
               RETURNING id, name, email""",
            (body.name, user_id),
        ).fetchone()
    if user is None:
        raise HTTPException(status_code=404, detail="User not found")
    return user


@app.delete("/users/{user_id}", tags=["users"], status_code=204, response_class=Response)
def delete_user(user_id: int):
    with get_connection() as conn:
        deleted = conn.execute(
            "DELETE FROM public.users WHERE id = %s RETURNING id", (user_id,)
        ).fetchone()
    if deleted is None:
        raise HTTPException(status_code=404, detail="User not found")
    return Response(status_code=204)

입력·출력 정의 읽기

Model은 여기서 데이터의 필드와 검증 규칙을 정의하는 Python class입니다. DB table을 만드는 코드가 아닙니다. UserCreate는 POST 입력, UserNamePatch는 PATCH 입력, UserResponse는 응답에 포함할 필드를 정의합니다.

Annotated는 기본 타입에 추가 규칙을 붙입니다. UserName의 기본 타입은 문자열 str입니다. StringConstraints는 앞뒤 공백을 제거하고 길이를 1~50자로 제한합니다. 예를 들어 " Ada "는 "Ada"가 되고 " "는 검증에 실패합니다.

EmailStr는 email 형식을 검사합니다. field_validator는 해당 필드를 추가로 처리하는 함수를 지정합니다. normalize_email은 검증된 email을 소문자로 바꿉니다. ConfigDict(extra="forbid")는 정의하지 않은 입력 필드를 거부합니다.

POST 한 번 추적하기

  1. FastAPI가 요청 body를 UserCreate로 검사합니다. 잘못된 입력은 422가 됩니다.
  2. get_connection()으로 DB 연결을 엽니다.
  3. INSERT의 %s와 별도의 값 tuple을 전달합니다. 사용자 입력을 SQL 문자열에 직접 붙이지 않습니다.
  4. RETURNING으로 실제 생성된 id, name, email을 받습니다.
  5. with 블록이 정상 종료되면 변경을 확정하고 연결을 닫습니다.
  6. UserResponse에 정의된 필드만 201 응답으로 보냅니다.

email 중복으로 users_email_key constraint를 위반하면 with 블록이 변경을 취소합니다. 그 후 except가 해당 오류를 409로 바꿉니다. 다른 DB 오류는 409로 숨기지 않습니다.

password_hash에는 실습용 !dummy-no-login을 저장합니다. 실제 로그인 비밀번호의 hash가 아니므로 이 코드는 회원가입 기능이 아닙니다. PATCH는 name만 변경합니다. DELETE 성공은 204이며 응답 body가 없습니다.

동기 Psycopg를 사용하는 endpoint는 def로 작성합니다. FastAPI는 이 함수를 thread pool에서 실행합니다. async def 안에 동기 DB 호출을 직접 넣지 않습니다.

확인: main.py가 길어졌다는 이유만으로 오늘 파일을 나누나요?

아니요. 오늘은 CRUD의 동작을 먼저 확인합니다. 8주차에는 각 코드의 역할과 변경 이유를 구별한 다음 파일을 나눕니다.

6. 한 사용자로 끝까지 따라가기

명령 대신 Swagger UI로 먼저 실습해도 됩니다. 각 endpoint의 Try it out을 누른 뒤 같은 body를 입력합니다. 아래 curl은 macOS/Linux 터미널 기준입니다. PowerShell에서는 Swagger UI를 쓰면 따옴표 차이를 피할 수 있습니다.

6-1. POST: 생성된 id 기록

curl -i -X POST http://127.0.0.1:8000/users \
  -H 'Content-Type: application/json' \
  -d '{"name":"Study 01","email":"study01.w07.001@example.com"}'

study01은 자기 계정 이름으로, 다른 팀원은 study02 등으로 email을 바꿉니다. 예상 HTTP status는 201입니다. 응답의 id를 기록합니다. 이 시점에는 이미 commit되어 다음 요청에서 읽을 수 있어야 합니다.

{"id":31,"name":"Study 01","email":"study01.w07.001@example.com"}

위 31은 예시입니다. 실제 응답 id를 아래의 YOUR_ID 자리에 넣으세요.

6-2. GET: 저장됐는지 확인

curl -i http://127.0.0.1:8000/users/YOUR_ID

200과 생성 당시 이름·email이 나와야 합니다. 기본 GET /users는 처음 20개만 반환하므로 새 사용자가 목록에 안 보일 수 있습니다. 생성된 id로 직접 조회하세요. 팀장은 학생이 알려 준 id를 자신의 API나 SQL Editor에서 조회해 같은 DB를 사용한다는 것도 보여 줄 수 있습니다.

6-3. PATCH: 이름만 변경

curl -i -X PATCH http://127.0.0.1:8000/users/YOUR_ID \
  -H 'Content-Type: application/json' \
  -d '{"name":"Study 01 Updated"}'

200 응답에서 name이 바뀌고 email은 유지되어야 합니다. 한 번 더 GET해서 DB 값도 변경됐는지 확인합니다. 여기서 서버를 Ctrl+C로 종료했다 다시 켜고 GET하면 수정한 데이터가 그대로 남아야 합니다.

6-4. DELETE: body 없는 성공

curl -i -X DELETE http://127.0.0.1:8000/users/YOUR_ID

204이며 body가 없어야 합니다. 같은 id를 GET하면 404입니다. DELETE를 한 번 더 보내도 이번 API 계약에서는 404를 반환합니다. 응답 status가 달라도 “row가 없는 상태”는 같으므로 DELETE의 idempotent한 결과와 모순되지 않습니다.

팀장 시연: rollback하면 row가 남을까?

학생 계정으로 실행할 별도 Python 코드입니다. email의 study01 부분은 자기 계정으로 바꿉니다. 기존 row와 충돌하지 않도록 고유 email을 생성합니다. 일부러 예외를 발생시키고 새 연결에서 확인합니다.

from uuid import uuid4
from app.database import get_connection

email = f"study01.rollback.{uuid4().hex}@example.com"
try:
    with get_connection() as conn:
        conn.execute(
            "INSERT INTO public.users (name, email, password_hash) VALUES (%s, %s, %s)",
            ("Rollback demo", email, "!dummy-no-login"),
        )
        raise RuntimeError("이번 작업을 취소합니다")
except RuntimeError:
    pass

with get_connection() as conn:
    print(conn.execute(
        "SELECT id FROM public.users WHERE email = %s", (email,)
    ).fetchone())  # None

결과는 None이어야 합니다. INSERT에서 id가 배정됐더라도 rollback 뒤 그 id 번호가 다시 쓰인다고 보장되지 않습니다. identity sequence에 빈 번호가 생기는 것은 정상입니다.

8. 완료 기준과 복습

  • □ 모든 팀원이 자기 DB role로 공용 프로젝트에 연결했다.
  • □ 자신의 email로 생성하고 실제 응답 id를 기록했다.
  • □ 이름만 수정했을 때 email이 유지된다.
  • □ 서버 재시작 후에도 변경된 데이터가 조회된다.
  • □ 중복 email은 409, 잘못된 입력은 422, 없는 사용자는 404다.
  • □ 삭제 성공은 204이며 재조회는 404다.
  • □ .env.local은 Git에 포함되지 않는다.
  • □ commit과 close의 차이를 설명할 수 있다.

팀원별 제출: 생성·수정·삭제의 status와 response, 중복 email 오류 결과, “Session mode에서 commit해도 연결이 바로 끝나지 않는 이유” 한 문장. 인증 정보가 담긴 화면은 제출하지 않습니다.

복습 질문과 답
  1. POST에서 id를 보내지 않는 이유? → DB identity가 생성하고 RETURNING으로 실제 값을 받기 때문.
  2. 왜 SELECT 중복 확인만으로 충분하지 않나? → 동시에 들어온 요청 사이에 경쟁이 생길 수 있으므로 UNIQUE가 최종 보장.
  3. 왜 connection을 닫아야 하나? → 사용이 끝난 연결 자원을 반환하기 위해. 특히 Session mode는 연결이 열려 있는 동안 DB 연결을 점유할 수 있음.
  4. 한 학생이 수정한 값이 다른 학생에게도 보이는 이유? → 같은 프로젝트·database·table을 사용하고 변경을 commit했기 때문.
  5. 이 서비스에 로그인해도 되나? → 아직 인증 기능이 없고 dummy placeholder만 사용하므로 로그인 수업 전 단계.
