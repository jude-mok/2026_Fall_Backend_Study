0. 오늘 어디까지 할까요?¶

오늘의 결과물은 README와 .gitignore가 있고, 의미 있는 커밋이 4개 이상 기록된 개인 연습 저장소입니다. Python이나 FastAPI 실행은 아직 필요하지 않습니다. 브랜치 분기, PR, merge와 rebase는 2주차에서 배웁니다.

  • 저장·add·commit·push가 각각 무엇을 바꾸는지 말할 수 있다.
  • status를 읽고 다음 행동을 결정할 수 있다.
  • 커밋 전에 포함될 내용을 확인하고, 잘못 선택한 파일을 제외할 수 있다.
  • GitHub에서 업로드된 파일과 커밋을 확인할 수 있다.

설치와 GitHub 로그인은 미리 준비하세요. 실습은 자기 속도에 맞춰 진행하고 선택 실습은 복습할 때 해도 됩니다.

실습 운영: 내 레포에서 만들고, 참고 답안과 비교하기

각자 본인 GitHub 계정에 backend-study 저장소를 새로 만들고 14주 동안 이어서 사용합니다. 파일 작성, commit, push는 모두 본인의 저장소에서 진행합니다. 같은 이름이어도 계정이 다르면 별개의 저장소입니다.

Jude의 GitHub — 참고 답안 저장소는 설명과 구현 예시를 확인하는 곳입니다. 이번 실습은 이 저장소를 fork하거나 clone해서 제출하는 방식이 아니라, 빈 개인 저장소에서 직접 시작합니다. 공동 저장소의 collaborator 등록이나 참고 답안 저장소로의 push·PR 제출은 필요하지 않습니다.

  1. 먼저 해당 주차의 설명을 읽고 개인 레포에서 직접 구현합니다.
  2. 막히면 참고 답안의 관련 파일과 변경 이유를 비교합니다. 최신 코드는 이후 주차 내용을 포함할 수 있으므로 지금 배우는 범위부터 확인합니다.
  3. 자기 결과를 확인한 뒤 본인 말로 커밋 메시지를 적고 개인 레포에 push합니다.
  4. 참고 답안과 자신의 결과를 비교해 봅니다. 코드나 커밋 ID가 같을 필요는 없습니다.

1. Git은 어떤 문제를 해결할까요?¶

README_최종.md, README_진짜최종.md처럼 복사본을 늘리면 어느 버전이 맞는지, 왜 바꿨는지 알기 어렵습니다. Git은 원하는 시점의 파일 상태에 설명을 붙여 기록합니다. 나중에 이전 내용을 확인하거나 두 시점의 차이를 비교할 수 있습니다.

이름하는 일예시
Git내 컴퓨터에서 파일의 버전을 관리하는 도구인터넷 없이도 커밋하고 이력 보기
GitHubGit 저장소를 온라인에 보관하고 협업하는 서비스다른 사람이 내 커밋을 보고 리뷰하기
저장소(repository)Git이 버전 관리를 하는 프로젝트일반적인 로컬 저장소는 작업 파일과 숨김 .git 폴더로 구성

.git에는 이력과 설정 등이 들어 있습니다. 일반 폴더를 만들었다고 Git 저장소가 되는 것은 아닙니다. git init으로 관리 정보를 만들어야 합니다. 실습 중 .git을 직접 편집하거나 삭제하지 마세요.

2. 처음이라면 여기부터: 실습 준비¶

준비물: Git, 텍스트 편집기(예: VS Code), GitHub 계정. macOS는 터미널, Windows는 Git 설치에 포함된 Git Bash를 사용하세요. 아래 파일 생성 명령은 Bash/Zsh 기준이며 PowerShell에서는 그대로 동작하지 않을 수 있습니다. 설치는 Git 공식 설치 안내를 따르세요.

git --version

git version 2.x.x처럼 버전이 나오면 준비되었습니다. 이 문서는 git init -b를 지원하는 Git 2.28 이상을 전제로 합니다.

터미널 기초뜻
pwd현재 위치를 확인한다.
ls현재 폴더의 파일 목록을 본다.
mkdir 폴더이름새 폴더를 만든다.
cd 폴더이름해당 폴더로 이동한다. cd ..은 상위 폴더로 간다.
명령 실행한 줄 입력 후 Enter. 예제에는 $ 같은 프롬프트 표시를 입력하지 않는다.

편집기에서 파일을 고쳤다면 먼저 저장하세요. Git은 디스크에 저장된 내용을 읽습니다. 아래 실습은 이 스터디 프로젝트 밖의 새 연습 폴더에서 합니다. 파일 탐색기로 원하는 상위 폴더를 열고 그 위치에서 터미널을 여세요. 같은 이름의 폴더가 있으면 다른 이름을 사용하세요.

mkdir backend-study
cd backend-study
git init -b main
git status

예상 결과: On branch main, No commits yet. main은 현재 작업하는 브랜치 이름이며 아직 첫 커밋이 없습니다. Git의 표시 언어에 따라 문구는 달라질 수 있습니다.

다음은 커밋에 남길 작성자 정보입니다. 예시 이름과 이메일을 본인 정보로 바꾸세요. 이 실습에서는 이 저장소에만 설정합니다. GitHub 이메일 공개가 싫다면 계정의 이메일 설정에 표시된 noreply 주소를 사용하세요.

git config user.name "Your Name"
git config user.email "you@example.com"
git config --get user.name
git config --get user.email

이름·이메일 설정은 GitHub 로그인이나 권한 부여가 아닙니다. 컴퓨터 전체의 기본값으로 만들 때는 --global 옵션을 쓰지만, 수업에서는 기존 설정을 바꾸지 않아도 됩니다. GitHub 설정 안내

3. 저장·선택·기록을 구분하기¶

보고서를 작성하고, 제출할 버전을 골라, 제출 기록을 남긴다고 생각해 보세요. 이 비유에서 중요한 것은 편집 중인 내용과 제출 후보가 서로 다를 수 있다는 점입니다.

위치담고 있는 것바꾸는 행동
작업 디렉터리(working tree)지금 디스크에 저장된 파일편집하고 저장
스테이징 영역(index)다음 커밋에 사용할 파일 상태git add 파일명
로컬 커밋 이력선택한 상태와 작성자·메시지·부모 등의 기록git commit -m "설명"
GitHub 원격 저장소전송한 커밋과 브랜치git push
편집·저장
작업 파일→ add →스테이징→ commit →로컬 이력→ push →원격 이력

커밋은 선택된 변경을 반영한 프로젝트의 추적 대상 파일 전체 상태를 가리킵니다. 수정한 파일만 들어 있는 압축파일이라는 뜻은 아닙니다. 변경되지 않은 내용은 재사용하며, 이전 커밋은 그대로 남습니다. Pro Git의 스냅샷 설명

HEAD는 현재 위치를 나타냅니다. 이 실습에서는 HEAD → main → 최신 커밋으로 이어집니다. 첫 커밋 전에는 main이라는 이름은 준비되어 있지만 아직 가리킬 커밋은 없습니다.

4. 손으로 따라 하는 첫 커밋¶

4-1. README를 만들고 상태 보기

printf '# Backend Study\n' > README.md
git status
git diff

printf는 글자를 출력하고, \n은 줄바꿈입니다. >는 파일을 만들거나 기존 내용을 덮어씁니다. 이후에 나오는 >>는 끝에 덧붙입니다. 편집기에서 같은 내용을 작성하고 저장해도 됩니다.

README.md는 프로젝트 안내문이며 .md는 Markdown 문서라는 뜻입니다. status에는 Untracked files 아래 README.md가 나옵니다. 아직 추적 대상으로 등록되지 않은 새 파일은 일반 git diff에 내용이 나오지 않습니다. 출력이 없다고 변경이 없는 것은 아닙니다.

4-2. 다음 커밋 후보에 넣기

git add README.md
git status
git diff --staged

status에는 Changes to be committed와 new file: README.md가 나옵니다. --staged 결과에 +# Backend Study가 보이면 후보에 첫 줄이 들어간 것입니다. 첫 커밋 전에는 마지막 커밋이 없으므로 staged diff는 준비된 전체 내용을 보여 줍니다.

4-3. 이유를 붙여 기록하기

git commit -m "docs: add study introduction"
git status
git log --oneline

-m 뒤 따옴표 안은 커밋 메시지입니다. 성공하면 커밋 ID와 메시지가 출력되고 status에는 nothing to commit, working tree clean이 나옵니다. log 첫 부분의 짧은 영숫자는 커밋 식별자라 사람마다 다릅니다. clean은 미기록 변경이 없다는 뜻이지 GitHub 업로드 완료라는 뜻은 아닙니다.

4-4. 한 번 더 반복하기

printf '\nGoal: learn backend fundamentals.\n' >> README.md
git diff
git add README.md
git diff --staged
git commit -m "docs: describe study goal"
git log --oneline

성공 기준: 커밋 2개가 최신순으로 보입니다. 긴 출력 화면에서 빠져나오지 못하면 q를 누르세요.

명령비교/관찰 대상언제 쓰나
git status파일별 변경 상태현재 상황부터 파악할 때
git diff스테이징 → 작업 파일 차이아직 선택하지 않은 수정 확인
git diff --staged마지막 커밋 → 스테이징 차이이번 커밋에 반영될 변경 확인
git log --oneline커밋 이력이미 기록한 작업 확인

diff의 -는 비교 기준 쪽에 있던 줄, +는 새 쪽에 있는 줄입니다. 수정은 보통 삭제와 추가로 표현됩니다. @@는 변경 구간의 줄 번호 정보이며 오류 표시가 아닙니다. git diff 문서

5. 가장 중요한 실험: add 뒤에 다시 수정하면?¶

지금부터는 명령을 실행하기 전에 결과를 예상해 보세요. 앞의 커밋 2개가 있는 깨끗한 상태에서 시작합니다.

printf '\nStack: Python\n' >> README.md
git add README.md
printf 'Framework: FastAPI\n' >> README.md
git status --short
git diff
git diff --staged

예상 status: MM README.md. 첫 M은 마지막 커밋과 스테이징이 다르다는 뜻, 둘째 M은 스테이징과 작업 파일이 다르다는 뜻입니다. 같은 파일이 staged와 unstaged에 동시에 나오는 것은 정상입니다. status 표시 규칙

시점작업 파일의 추가 내용스테이징의 추가 내용
Python 작성 후 addStack: PythonStack: Python
FastAPI를 추가로 저장Stack: Python + Framework: FastAPIStack: Python만 있음
예상해 보기: 지금 커밋하면 FastAPI도 기록될까요?

아니요. 일반적인 git commit -m은 스테이징에 준비한 내용을 기록하므로 Python 줄만 새로 기록됩니다. add는 이후 편집을 실시간으로 따라가지 않습니다. FastAPI까지 넣으려면 다시 add해야 합니다.

git commit -m "docs: choose Python stack"
git show HEAD:README.md
git diff

git show HEAD:README.md는 최신 커밋 속 파일을 읽습니다. 여기에는 FastAPI 줄이 없고, 작업 파일에는 남아 있어 diff에 표시됩니다. 실제 파일이 삭제된 것이 아닙니다. 확인했으면 남은 수정도 기록하세요.

git add README.md
git diff --staged
git commit -m "docs: choose FastAPI framework"
git status

성공 기준: 커밋이 4개이며 상태가 clean입니다. add는 실행한 시점의 내용을 선택한다는 규칙으로 이 실험 전체를 설명할 수 있어야 합니다. git add 공식 동작

6. 기록하지 않을 파일과 잘못된 선택 되돌리기¶

백엔드 프로젝트에는 비밀번호가 담긴 .env, 재설치 가능한 가상환경 .venv, 실행 중 생기는 캐시가 있습니다. 다음은 Python 프로젝트용 예시입니다. 이 실습의 .env에는 실제 비밀번호를 넣지 않습니다.

printf 'DEMO_KEY=not-a-real-secret\n' > .env
git add .env
git status --short
git restore --staged .env
git status --short

앞 실습처럼 첫 커밋이 이미 존재하는 상태에서 실행합니다. 결과는 A .env에서 ?? .env로 바뀝니다. 후보에서만 빠졌고 디스크 파일은 남습니다. 첫 커밋 전에는 HEAD가 없어 같은 restore 명령이 실패할 수 있습니다.

printf '.venv/\n__pycache__/\n.pytest_cache/\n.ruff_cache/\n.env\n.env.*\n!.env.example\n*.log\n' > .gitignore
printf 'DEMO_KEY=replace-me\n' > .env.example
git check-ignore -v .env
git status --short
git add .gitignore .env.example
git diff --staged
git commit -m "chore: ignore local files and add config template"

check-ignore -v는 어떤 규칙이 파일을 제외하는지 보여 줍니다. status에는 .env가 안 보이고 .gitignore와 .env.example만 후보가 되어야 합니다. !는 예외 규칙이라 .env.example은 공유할 수 있습니다. .env.example에는 필요한 항목 이름과 가짜 예시값만 적습니다.

.gitignore는 이미 추적 중인 파일에는 소급 적용되지 않습니다. 이미 추적한 일반 파일은 git rm --cached 파일명으로 추적에서 제외한 뒤 그 변경을 커밋할 수 있습니다. 디스크 파일은 남지만 과거 커밋은 지워지지 않습니다. 실제 비밀값을 커밋·공유했다면 키를 폐기·교체하고 이력 정리도 별도로 해야 합니다. gitignore 문서

원하는 결과명령작업 파일
커밋 후보에서만 빼기(커밋 존재 시)git restore --staged 파일명유지됨
추적 파일의 미선택 수정을 버리기git restore 파일명스테이징 내용으로 덮어씀. 해당 수정이 사라짐

두 명령은 결과가 다릅니다. 수정 내용을 보존하려면 --staged를 빼먹지 마세요. restore의 대상과 기본 원본

7. 내 기록을 GitHub에 공유하기¶

여기까지의 커밋은 전부 내 컴퓨터에 있습니다. GitHub 저장소를 만들고 연결해야 온라인으로 공유할 수 있습니다. origin은 원격 주소의 별명이고 main은 브랜치 이름입니다.

  1. GitHub에 로그인하고 새 저장소 만들기(New repository)를 엽니다.
  2. 이름을 backend-study로 정하고 공개 범위를 선택합니다.
  3. 이번에는 README, .gitignore, license를 자동 생성하지 않는 빈 저장소로 만듭니다. 로컬에 이미 이력이 있기 때문입니다.
  4. 본인 계정에 생성된 저장소의 HTTPS 주소를 복사합니다. 아래 YOUR-USERNAME을 실제 계정명으로 바꾸거나 복사한 주소 전체를 사용합니다.
git remote add origin https://github.com/YOUR-USERNAME/backend-study.git
git remote -v
git push -u origin main

push 전 확인: git remote -v의 주소가 본인 계정의 backend-study인지 확인하세요. 참고 답안의 jude-mok/2026_Fall_Backend_Study를 origin으로 입력하지 않습니다.

remote add는 주소만 등록합니다. push는 필요한 커밋을 전송하고 원격 브랜치를 갱신합니다. -u는 이후 push 등의 기준이 될 upstream 연결을 설정합니다. 이후 같은 브랜치에서는 일반적으로 git push만으로 올릴 수 있습니다.

HTTPS 인증 창이 뜨면 설정된 자격 증명 도구의 로그인 절차를 따릅니다. GitHub 계정 비밀번호를 터미널에 넣는 방식은 지원되지 않습니다. 필요하면 Git Credential Manager 또는 개인 액세스 토큰을 사용하세요. 토큰은 문서·명령 예시·스크린샷에 남기지 않습니다. 공식 인증 설정 안내

성공 기준: GitHub 페이지를 새로고침하면 README 내용과 커밋 목록이 보이고 .env는 없어야 합니다. 로컬에서 git log -1 --oneline으로 본 최신 ID와 GitHub 최신 커밋의 ID를 비교하세요. 참고: 기존 로컬 저장소 업로드

다른 사람이 이미 만든 저장소라면?

처음부터 만드는 이번 실습은 init을 사용했습니다. 기존 저장소를 받아 시작할 때는 프로젝트 밖의 폴더에서 git clone 저장소URL을 사용합니다. clone은 파일과 이력을 가져오고 보통 origin도 설정합니다. ZIP 다운로드에는 Git 이력이 포함되지 않습니다. clone한 폴더에서 다시 remote add origin을 할 필요는 없습니다. 이 내용은 개념 참고이며 이번 개인 레포 실습에서는 앞의 init 방식으로 진행합니다.

8. 실무에서 쓰는 Naming Convention¶

Naming convention은 “같은 종류의 대상에는 같은 방식으로 이름을 붙이자”는 약속입니다. 이름만 보고 용도와 변경 목적을 파악하고 검색하기 쉽게 만듭니다. 모든 회사가 따르는 단 하나의 규칙은 없습니다. 실제 팀에서는 해당 저장소의 README·CONTRIBUTING과 기존 규칙을 먼저 확인합니다. 아래는 실무 관례와 공개 표준을 바탕으로 정한 이번 스터디의 규칙입니다.

8-1. 이름 모양부터 구분하기

표기법예시구분 방법
kebab-casebackend-study소문자 단어를 하이픈(-)으로 연결
snake_caseuser_service소문자 단어를 밑줄(_)로 연결
PascalCaseUserService모든 단어의 첫 글자를 대문자로
camelCaseuserName첫 단어는 소문자, 이후 단어 첫 글자는 대문자로. 이번 Python 변수에는 사용하지 않음
UPPER_SNAKE_CASEMAX_RETRIES대문자 단어를 밑줄로 연결

8-2. 저장소·파일·브랜치 이름

대상이 스터디의 규칙예시
개인 저장소영문 소문자 + 하이픈, 공백 없이 목적 표현backend-study
기본 브랜치main1주차는 main에서 실습
작업 브랜치종류/짧은-작업-설명feature/signup, fix/login-error, docs/setup-guide, chore/update-dependencies
일반 문서 파일영문 소문자 + 하이픈setup-guide.md, week-01-notes.md
관례적인 특수 파일정해진 이름 유지README.md, .gitignore, pyproject.toml
Python 모듈 파일영문 소문자 + 필요시 밑줄user_service.py

브랜치 생성은 2주차에 실습합니다. feature/는 기능 작업, fix/는 버그 수정입니다. 이슈 관리 도구를 쓰는 팀에서는 feature/123-user-signup처럼 작업 번호를 넣기도 합니다. 이번 스터디에서는 번호가 없어도 됩니다. mybranch, test2, final-final처럼 목적을 알 수 없는 이름은 피하세요. 참고 답안 저장소의 기존 이름은 그대로 사용하며 새 개인 저장소에 위 규칙을 적용합니다. GitLab의 브랜치 이름 안내

8-3. 커밋 메시지: Conventional Commits

커밋에는 type: 설명 형식을 사용합니다. 콜론 다음에는 공백 하나를 넣습니다. 범위를 밝히고 싶으면 type(scope): 설명으로 씁니다. 예를 들어 fix(auth): reject expired tokens의 auth는 인증 영역입니다. scope는 선택 사항입니다. Conventional Commits 공식 명세

type언제 쓰나스터디 예시
feat새 기능feat: add signup endpoint
fix잘못된 동작 수정fix: reject duplicate email
docs문서 변경docs: add study goals
refactor기능·동작을 유지하며 코드 구조 개선refactor: extract user lookup
test테스트 추가·수정test: cover invalid password
style동작에 영향 없는 코드 서식 변경style: format user router
chore기타 유지보수·개발 설정 정리chore: ignore local files
build / ci빌드·의존성 / 자동 검사 설정build: update fastapi dependency, ci: run pytest on push

명세는 feat와 fix의 의미를 정하고 다른 type도 허용합니다. 나머지 분류는 팀이 합의하는 관례입니다. 이번 스터디는 의존성 변경을 build, 기타 개발 설정을 chore로 구분합니다. 기존 실무 팀에서 다르게 정했다면 그 규칙을 따릅니다.

  • type은 소문자로 통일합니다. 설명은 한국어도 가능합니다: docs: 학습 목표 추가.
  • 영어 설명은 add, fix, remove처럼 행동으로 시작하고 한 줄로 구체적으로 적습니다.
  • update, 수정함만 적기보다 무엇을 바꿨는지 씁니다. 이유가 길면 제목 다음 빈 줄을 두고 본문에 적습니다.
  • README 오타 수정은 docs, 서버 오류 수정은 fix입니다. 새 기능 없이 코드만 정리했다면 feat가 아니라 refactor입니다.
  • 서로 다른 목적이 섞였다면 커밋을 나눕니다. 접두사를 붙이는 것만으로 좋은 커밋이 되지는 않습니다.

참고로 호환성을 깨는 변경은 feat(api)!: rename user response field처럼 !나 BREAKING CHANGE: footer로 표시합니다. 기존 사용 코드가 바뀌어야 하는 변경이라는 뜻이며 1주차에서는 직접 사용할 필요가 없습니다.

8-4. 앞으로 쓸 Python 이름 규칙 미리 보기

Python에서는 PEP 8에 맞춰 함수·변수는 get_user, user_email처럼 snake_case, 클래스는 UserService처럼 PascalCase, 상수는 MAX_RETRIES처럼 대문자와 밑줄을 사용합니다. 저장소 이름의 하이픈을 Python 변수나 모듈 이름에 그대로 쓰지 마세요. 코드는 이후 주차에서 작성합니다.

9. 작은 커밋 만들기 · 선택 실습¶

좋은 커밋의 크기는 줄 수보다 목적에 달려 있습니다. “README 오타 수정”과 “서버 동작 변경”이 섞이면 검토와 문제 추적이 어려워집니다. docs:나 chore:는 메시지 관례이며 Git이 강제하는 문법이 아닙니다. 한국어 메시지도 괜찮습니다.

모호한 메시지목적이 보이는 메시지
updatedocs: add weekly study schedule
fixdocs: correct setup command typo
작업 완료docs: explain project learning goals

선택: 한 파일의 변경도 나누기

README의 제목과 맨 아래 학습 계획을 서로 떨어진 위치에서 수정하고 저장합니다. 아래 명령으로 변경 덩어리(hunk)를 하나씩 선택합니다.

git add -p README.md
git diff --staged
git diff

y는 이 덩어리 선택, n은 건너뛰기, s는 나눌 수 있을 때 분할, q는 종료입니다. 한 덩어리로 나오고 분할할 수 없다면 억지로 진행하지 말고 git restore --staged README.md로 선택을 풀어 보세요. 처음에는 파일별로 목적을 나누는 것만 익혀도 됩니다. 선택한 내용을 검토한 뒤 적절한 메시지로 커밋하고 남은 수정도 마무리합니다.

11. 설명할 수 있으면 이해한 것: 질문과 해설¶

1. Git과 GitHub는 어떻게 다른가요?

Git은 로컬에서 버전 관리를 하는 도구, GitHub는 저장소를 호스팅하고 협업 기능을 제공하는 서비스입니다. 로컬 커밋은 인터넷 없이 가능하며 공유에는 push가 필요합니다.

2. 왜 바로 commit하지 않고 add를 하나요?

여러 수정 중 이번 기록에 넣을 내용을 고르기 위해서입니다. 예를 들어 완성한 설명과 아직 작성 중인 계획을 따로 기록할 수 있습니다.

3. README를 A로 바꾸고 add, B로 바꾸고 commit하면?

일반적인 commit -m은 add 시점의 A를 기록합니다. 작업 파일에는 B가 남고, A와 B 차이는 아직 스테이징되지 않은 수정으로 보입니다.

4. commit 후 스테이징 영역은 비어 있나요?

아니요. 스냅샷 후보는 남지만 최신 커밋과 같아서 커밋할 변경이 없는 상태입니다.

5. diff가 비었는데 status에 새 파일이 보이는 이유는?

추적되지 않은 새 파일 내용은 일반 diff의 비교 대상이 아닙니다. 파일을 읽어 확인하고 add한 뒤 diff --staged로 확인할 수 있습니다.

6. .gitignore에 썼는데 GitHub에서 파일이 보이는 이유는?

이미 커밋·추적된 파일에는 ignore가 소급 적용되지 않습니다. 추적 제외를 커밋하고 push해도 과거 이력은 남습니다.

7. restore --staged와 restore의 차이는?

전자는 스테이징을 변경하며 작업 파일을 유지합니다. 후자는 기본적으로 작업 파일을 스테이징 내용으로 되돌려 미선택 수정을 버립니다.

8. working tree clean이면 push도 끝났나요?

아니요. 작업 파일·스테이징·최신 커밋 간 미기록 변경이 없다는 뜻입니다. 원격 공유 여부는 별도로 확인해야 합니다.

9. origin은 GitHub가 정한 특별한 서버인가요?

아니요. 원격 주소에 붙인 관례적인 별명입니다. 다른 이름도 가능하고 주소는 remote -v로 확인합니다.

10. 저장과 커밋은 어떻게 다른가요?

저장은 작업 파일을 바꾸고, 커밋은 선택된 상태를 메시지와 함께 이력에 남긴다고 구분합니다. add 이후 추가 편집 실험으로 차이를 직접 보여 줍니다.

복습 완료 기준: 3번을 상태 표 없이 설명하고, 5번과 8번에서 어떤 명령으로 확인할지 말할 수 있어야 합니다.

12. 공식 참고 자료와 다음 주 연결¶

명령의 정확한 동작이 궁금할 때는 다음 자료를 참고하세요. 수업에서 전부 읽을 필요는 없습니다.

  • Git 공식 튜토리얼
  • git add — 후보 내용을 갱신하는 규칙
  • git diff — 비교 기준
  • git status — 상태 표시
  • git restore — 복원 대상
  • gitignore — 제외 패턴
  • GitHub — Git 설정과 인증
