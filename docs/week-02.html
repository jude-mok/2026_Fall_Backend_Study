Week 02 — Git & GitHub II: 브랜치로 작업하고 함께 합치기

지난주에는 변경을 기록했습니다. 이번 주에는 GitHub에서 변경을 공유하고 검토한 뒤 main에 합치는 과정을 배웁니다. 이전: Git 기본기 · 전체 커리큘럼

0. 오늘 어디까지 할까요?¶

오늘의 결과물은 작업 브랜치에서 README를 수정하고, PR에서 변경을 검토한 뒤 main에 반영한 개인 저장소입니다. 아직 FastAPI 코드를 작성할 필요는 없습니다.

  • 브랜치를 나누는 이유를 설명할 수 있습니다.
  • main, origin, origin/main을 구분할 수 있습니다.
  • fetch와 pull이 무엇을 바꾸는지 예상할 수 있습니다.
  • PR을 만들고 수정 사항을 추가한 뒤 병합할 수 있습니다.
  • 충돌을 해결하고 merge와 rebase의 차이를 설명할 수 있습니다.

리드 진행 순서: 개념 설명 20분 → 브랜치·PR 실습 30분 → 충돌 실습 20분 → merge/rebase 비교와 복습 20분. 진행 속도에 따라 rebase 실습은 선택 과제로 남겨도 됩니다.

“지난주에는 내 변경을 기록했습니다. 오늘은 검토가 끝난 변경을 다른 작업과 합치는 방법을 배웁니다.”

1. 왜 브랜치를 나눠서 작업할까요?¶

지민은 로그인 기능, 수현은 게시글 조회 기능을 만든다고 생각해 봅시다. 둘 다 main에 미완성 코드를 올리면 안정적으로 실행되는 버전과 작업 중인 버전을 구분하기 어렵습니다. 그래서 main은 검토한 상태로 유지하고, 작업마다 브랜치를 만들어 준비된 변경만 합칩니다.

브랜치는 별도의 폴더 복사본이 아니라 커밋을 가리키는 이동 가능한 이름입니다. 커밋하면 현재 브랜치가 새 커밋을 가리킵니다. 브랜치를 바꾸면 Git이 작업 폴더의 파일을 해당 버전에 맞춥니다.

main             A──B
                    ├──C──D  feature/login
                    └──E──F  feature/posts

로그인 브랜치에서 커밋해도 main에는 바로 반영되지 않습니다. 각각 검토한 뒤 합칠 수 있어 작업 범위와 변경 이유를 파악하기 쉽습니다. 브랜치를 사용해도 같은 부분을 다르게 수정하면 충돌은 생길 수 있습니다.

예상해 보기: “로그인 기능이 아직 절반만 완성됐다면, 팀원들이 사용하는 main에 바로 넣어도 될까요?”

브랜치는 Git의 기능이고 GitHub 없이도 만들 수 있습니다. GitHub는 그 브랜치를 공유하고 PR로 검토하는 장소입니다.

2. 원격 저장소: remote, origin, clone¶

origin은 저장소 주소에 붙인 별명입니다

Git은 로컬에서 버전을 관리하는 도구이고, GitHub는 저장소를 온라인에 보관하고 협업하는 서비스입니다. remote는 다른 저장소와의 연결이며 origin은 그 연결에 관례적으로 붙이는 이름입니다. GitHub 자체나 브랜치 이름이 아닙니다.

git remote -v

출력 예시입니다. YOUR_ID에는 본인의 GitHub 계정 이름이 표시되어야 합니다.

origin  https://github.com/YOUR_ID/backend-study.git (fetch)
origin  https://github.com/YOUR_ID/backend-study.git (push)

fetch 주소는 가져올 곳, push 주소는 보낼 곳입니다. 이번 실습에서는 같은 주소를 사용합니다. 연결이 없다면 git remote add origin 저장소URL로 등록하고, 잘못된 주소라면 git remote set-url origin 올바른URL로 수정합니다. 연결 등록만으로 커밋이 업로드되지는 않습니다.

clone은 기존 저장소를 처음 가져올 때 사용합니다

이미 1주차 저장소가 있는 컴퓨터에서는 다시 clone하지 않습니다. 새 컴퓨터에서 시작하거나 기존 프로젝트를 처음 받을 때, 프로젝트 밖의 폴더에서 다음을 실행합니다. YOUR_ID는 실제 계정 이름으로 바꿉니다.

git clone https://github.com/YOUR_ID/backend-study.git
cd backend-study

일반적인 clone은 파일과 이력을 가져오고 origin을 등록합니다. clone 후에는 remote add origin을 다시 실행할 필요가 없습니다. ZIP 다운로드에는 Git 이력이 들어 있지 않습니다.

main과 origin/main은 어디에 있을까요?

이름의미
main내 컴퓨터의 로컬 브랜치
GitHub의 main원격 저장소에 있는 브랜치
origin/main내 Git이 마지막으로 확인한 원격 main의 위치

origin/main은 내 컴퓨터에 있는 원격 추적 브랜치(remote-tracking branch)입니다. GitHub를 실시간으로 보여주지 않으므로 원격 정보를 가져와 갱신해야 합니다.

3. fetch, pull, push는 무엇을 바꿀까요?¶

fetch: 원격의 최신 정보를 가져오기

git fetch origin

커밋과 브랜치 정보를 가져와 origin/main 등을 갱신합니다. 현재 작업 브랜치와 작업 파일에 변경을 자동으로 합치지는 않습니다.

                 fetch 전       fetch 후
GitHub main      A──B──C        A──B──C
내 origin/main   A──B           A──B──C
내 main          A──B           A──B

“팀원이 무엇을 바꿨는지 확인한 상태입니다. 아직 내 main에 적용한 것은 아닙니다.”

pull: 가져온 변경을 현재 브랜치에 통합하기

git switch main
git pull --ff-only origin main

pull은 fetch 후 현재 브랜치에 변경을 통합합니다. 이번에는 --ff-only를 명시합니다. 내 main에서 원격 main으로 브랜치 위치만 앞으로 옮길 수 있을 때 업데이트하고, 양쪽 이력이 갈라졌다면 멈춥니다. 멈췄을 때는 이력을 확인하고 merge 또는 rebase를 선택해야 합니다.

git pull --no-rebase는 merge 방식, git pull --rebase는 rebase 방식으로 통합합니다. 옵션 없는 pull의 동작은 설정과 버전에 영향을 받으므로 수업에서는 방식을 명시합니다. 작업 브랜치에서 git pull origin main을 실행하면 현재 작업 브랜치에 원격 main을 통합하려고 합니다.

push: 내 커밋을 원격 브랜치로 보내기

git push origin feature/health-route

로컬 feature/health-route의 커밋을 원격의 같은 이름 브랜치로 보냅니다. 수정만 하고 커밋하지 않은 내용은 올라가지 않습니다. push만으로 main에 합쳐지거나 PR이 자동 생성되지는 않습니다.

4. push -u의 upstream은 무엇일까요?¶

git push -u origin feature/health-route
git branch -vv

-u는 업로드하면서 현재 로컬 브랜치가 추적할 상대 브랜치도 설정합니다. 이 상대를 upstream branch라고 합니다. 여기서는 origin/feature/health-route입니다. 일반적인 기본 설정에서는 이후 해당 브랜치에서 git push만 입력해도 같은 곳으로 보냅니다. 인자 없는 pull도 이 추적 관계를 사용합니다.

별개의 용법: fork 협업에서는 내 복사본을 origin, 원본 저장소를 upstream이라는 remote 이름으로 등록하기도 합니다. 예를 들어 git remote add upstream 원본저장소URL입니다. 이때 upstream은 저장소 별명이며, 브랜치의 추적 설정과는 다릅니다. 이번 개인 저장소 실습에는 추가하지 않습니다.

git status의 ahead/behind도 마지막으로 확인한 원격 추적 정보와 비교한 결과입니다. 실제 원격과 비교하려면 먼저 fetch합니다.

5. 실습: 브랜치에서 PR까지¶

① 상태 확인 → main 최신화 → 작업 브랜치 생성

1주차 저장소 폴더에서 진행합니다. status에 미완료 변경이 있다면 먼저 해당 작업을 커밋하는 등 정리한 뒤 진행하세요.

git status
git switch main
git pull --ff-only origin main
git switch -c feature/health-route

switch -c는 브랜치를 만들고 이동합니다. 이미 있는 브랜치로 이동할 때는 git switch feature/health-route처럼 -c를 빼세요.

② README에 계획 작성 → 변경 확인 → 커밋

README.md 끝에 다음 내용을 추가합니다. 오늘은 계획만 작성하고 서버 구현은 이후 주차에 진행합니다.

## 서버 상태 확인 계획

- 요청: GET /health
- 정상 응답: 200 OK
- 응답 내용: {"status": "ok"}

git diff
git add README.md
git diff --staged
git commit -m "서버 상태 확인 기능 계획 추가"

커밋 메시지는 무엇을 바꿨는지 알 수 있게 씁니다. docs:는 팀에서 선택하는 문서 변경 분류이며 Git의 필수 문법이 아닙니다. 이번 예시는 자연스러운 한국어 설명을 사용합니다. 1주차 이름 규칙도 참고하세요.

③ 내 origin에 업로드

git push -u origin feature/health-route

GitHub에서 브랜치 선택 메뉴를 열어 feature/health-route와 main의 README를 비교합니다. 작업 브랜치에는 계획이 있고, main에는 아직 없어야 합니다.

④ GitHub에서 Pull Request 열기

본인 저장소의 Pull requests → New pull request로 이동합니다. base는 main, compare는 feature/health-route로 선택합니다. base는 변경을 받을 쪽, compare는 변경을 제안하는 쪽입니다.

PR은 “이 변경을 검토하고 합쳐 주세요”라는 요청입니다. git pull 명령과는 다릅니다. Files changed에서 의도한 파일과 내용만 포함되는지 확인하고 설명을 작성합니다.

제목: 서버 상태 확인 기능 계획 추가

변경 이유
서버가 응답하는지 확인할 공통 경로가 필요합니다.

변경 내용
GET /health의 응답 코드와 JSON 형식을 README에 정리했습니다.

확인한 내용
README 표시와 요청·응답 설명을 확인했습니다.
아직 서버 코드는 구현하지 않았습니다.

⑤ 리뷰를 읽고 같은 브랜치에서 수정

짝과 PR 링크를 공유하고 설명이 이해되는지 피드백을 받아 봅니다. 공개 저장소에서는 접근 가능한 팀원이 댓글을 남길 수 있고, 비공개 저장소는 접근 권한이 필요합니다. 이번 개인 실습은 자신의 PR을 직접 검토해도 됩니다. 자기 PR에 승인 리뷰를 남기는 대신 Files changed와 설명을 점검합니다.

리뷰 예시: “정상 상태에서 응답할 JSON 예시가 있으면 구현할 때 더 명확할 것 같습니다.” 피드백을 반영해 README를 수정했다면:

git add README.md
git commit -m "상태 확인 응답 설명 보완"
git push

기존 PR에 새 커밋이 추가됩니다. 수정할 때마다 새 PR을 열 필요는 없습니다. 실제 팀에서는 검토와 자동 검사 통과 여부, 병합 권한을 확인합니다.

⑥ PR 병합 → 로컬 main 업데이트

이번 기본 실습은 GitHub에서 Create a merge commit 방식이 허용되어 있다면 해당 방식으로 병합합니다. 저장소 설정에 따라 표시되는 방식은 다를 수 있습니다.

git switch main
git pull --ff-only origin main
git log --oneline --graph --decorate --all

로컬 main의 README에 계획이 보이면 완료입니다. 다음 작업은 최신 main에서 새 브랜치를 만들어 시작합니다. 작업을 마친 로컬 브랜치는 git branch -d feature/health-route로 삭제할 수 있습니다. squash/rebase 병합 후에는 Git이 병합 여부를 이력으로 확인하지 못해 삭제를 거절할 수 있으므로 바로 강제 삭제하지 말고 반영 여부부터 확인합니다.

6. 작업 중 main이 바뀌었다면? — merge와 rebase¶

다음은 설명용으로 같은 시작 상태를 비교한 예시입니다. 아래 두 방법을 순서대로 모두 실행하는 것이 아닙니다. 작업 브랜치에서 미완료 변경을 정리한 뒤 선택합니다.

A──B──C     origin/main
    \ 
     D──E   feature/example

merge: 기존 이력을 유지하며 합치기

git fetch origin
git merge origin/main

A──B──C       origin/main
    \  \ 
     D──E──M   feature/example

이처럼 갈라진 이력을 합치면 두 부모를 가진 병합 커밋 M이 생깁니다. D와 E는 그대로입니다. 이력이 갈라지지 않았다면 새 병합 커밋 없이 fast-forward가 가능할 수도 있습니다.

rebase: 새 기준 위에 내 변경을 다시 적용하기

git fetch origin
git rebase origin/main

A──B──C       origin/main
       \ 
        D'──E'   feature/example

D와 E의 변경을 C 뒤에 다시 적용합니다. 부모 등이 달라져 새 커밋 D′, E′가 만들어지므로 커밋 ID도 바뀝니다. 공유 브랜치의 이력을 임의로 다시 쓰면 다른 사람의 작업과 어긋납니다. 기본 실습에서는 merge를 사용하고 rebase는 개인 작업 브랜치에서 연습합니다.

아직 push하지 않은 브랜치라면 rebase 후 일반 push로 올릴 수 있습니다. 이미 올린 개인 브랜치의 이력을 바꾼 경우에는 일반 push가 거절될 수 있습니다. 팀이 허용하고 원격 변경을 검토한 경우에만 git push --force-with-lease origin feature/example을 사용합니다. main에는 사용하지 않습니다.

force-with-lease는 원격이 예상한 커밋을 가리키는지 검사합니다. 다른 사람의 변경을 자동으로 보존하지 않으며, 백그라운드 fetch가 예상 상태를 갱신할 수도 있습니다. 거절됐다고 fetch 후 무조건 재시도하지 말고 원격 변경을 먼저 확인합니다.

내 브랜치 갱신과 PR 병합은 방향이 다릅니다

작업방향과 목적
작업 브랜치에서 merge/rebase origin/main최신 main을 내 작업에 반영
GitHub에서 PR 병합검토한 내 작업을 main에 반영

GitHub의 Create a merge commit은 병합 커밋으로 연결하고, Squash and merge는 PR의 변경을 하나의 커밋으로 합치며, Rebase and merge는 변경 커밋들을 base 위에 다시 적용합니다. 팀의 이력 관리 규칙에 따라 선택합니다.

7. 실전 예제: 충돌을 직접 만들고 해결하기¶

실제 작업 파일 대신 conflict-practice.txt를 사용하는 별도 연습 브랜치에서 진행합니다. main에는 연습 커밋을 넣지 않습니다. 아래 이름이 이미 있거나 같은 파일이 있다면 새 이름으로 바꾸세요. 시작 전 작업 폴더가 깨끗한지 확인합니다.

① 공통 출발점 만들기

git status
git switch main
git switch -c practice/conflict-base
printf "스터디 시간: 미정\n" > conflict-practice.txt
git add conflict-practice.txt
git commit -m "충돌 연습의 공통 문장 추가"

② 같은 출발점에서 서로 다른 수정 만들기

git switch -c practice/time-a
printf "스터디 시간: 수요일 오후 7시\n" > conflict-practice.txt
git add conflict-practice.txt
git commit -m "수요일 스터디 시간 제안"

git switch practice/conflict-base
git switch -c practice/time-b
printf "스터디 시간: 목요일 오후 8시\n" > conflict-practice.txt
git add conflict-practice.txt
git commit -m "목요일 스터디 시간 제안"

git merge practice/time-a

마지막 명령은 의도적으로 충돌을 만듭니다. Git은 같은 줄의 어느 변경을 남길지 판단할 수 없습니다. 파일을 열면 다음과 비슷하게 보입니다.

<<<<<<< HEAD
스터디 시간: 목요일 오후 8시
=======
스터디 시간: 수요일 오후 7시
>>>>>>> practice/time-a

③ 최종 내용 결정 → add → 병합 완료

이 merge에서 HEAD 쪽은 현재 time-b, 아래쪽은 가져오는 time-a입니다. 양쪽 의도를 확인하고 최종 시간을 결정합니다. 연습에서는 “스터디 시간: 금요일 오후 7시”로 파일 전체를 바꾸고 충돌 표시를 모두 지웁니다.

git status
git add conflict-practice.txt
git diff --staged
git diff --check
git merge --continue
git log --oneline --graph --decorate --all

add는 해결한 최종 내용을 스테이징합니다. merge --continue에서 편집기가 열리면 병합 메시지를 저장하고 종료합니다. status에서 충돌이 사라지고 최종 문장이 맞는지 확인합니다. 코드 충돌이라면 표시 제거뿐 아니라 테스트도 필요합니다. 완료 후 git switch main으로 돌아옵니다.

진행 중인 병합을 취소하려면 git merge --abort를 사용합니다. 깨끗한 작업 상태에서 시작했다면 병합 전 상태로 돌아갑니다.

rebase 중 충돌이라면?

파일을 수정하고 add한 뒤 git rebase --continue를 실행합니다. 중단은 git rebase --abort입니다. 커밋을 하나씩 다시 적용하므로 충돌이 여러 번 생길 수 있습니다. rebase의 HEAD 쪽은 새 기준 위에 지금까지 재구성된 내용이므로 무조건 “원래 내 코드”라고 해석하지 않습니다.

“충돌은 Git이 망가졌다는 뜻이 아닙니다. 최종 결과를 사람이 판단해야 한다는 뜻입니다.”

8. 자주 사용하는 명령어와 용어¶

명령어하는 일
git status현재 브랜치와 파일 상태 확인
git remote -v원격 저장소 주소 확인
git branch -a로컬·원격 추적 브랜치 목록 확인
git branch -vv로컬 브랜치의 upstream 확인
git switch -c 브랜치명새 브랜치를 만들고 이동
git fetch origin원격 정보 갱신
git pull --ff-only origin main원격 main을 현재 브랜치에 fast-forward로 반영
git push -u origin 브랜치명업로드하고 추적 관계 설정
git log --oneline --graph --decorate --all커밋과 브랜치 관계 보기

이 명령들은 GitHub 전용 명령이 아니라 Git 명령입니다. GitHub에서는 Code에서 파일·브랜치·커밋을, Pull requests에서 변경 제안과 리뷰를, PR의 Files changed에서 차이를 확인합니다. 자동 검사가 설정된 저장소라면 Checks에서 결과를 확인합니다.

fast-forward는 브랜치 위치만 앞으로 이동하는 방식, conflict는 자동 통합이 멈춘 상태, code review는 변경의 정확성과 이해 가능성을 함께 검토하는 과정입니다.

10. 설명할 수 있으면 이해한 것: 질문과 해설¶

왜 main에서 바로 작업하지 않나요?

검토 전 변경을 분리하고, 준비된 작업만 main에 반영하기 위해서입니다. 브랜치가 충돌 자체를 없애지는 않습니다.

커밋했는데 GitHub에 보이지 않는 이유는?

커밋은 로컬 기록입니다. 올바른 원격 브랜치로 push했는지 확인합니다.

fetch했는데 내 main이 그대로인 이유는?

fetch는 origin/main 같은 원격 추적 정보를 갱신합니다. 로컬 main에 통합하는 단계가 따로 필요합니다.

origin/main은 GitHub의 main 그 자체인가요?

아닙니다. 내 Git이 마지막으로 확인한 원격 main의 위치입니다.

PR과 git pull은 같은 작업인가요?

PR은 GitHub에서 변경을 검토하고 병합하도록 요청하는 기능입니다. pull은 터미널에서 원격 변경을 가져와 현재 브랜치에 통합하는 Git 명령입니다.

rebase 후 커밋 ID가 달라지는 이유는?

새 기반 위에 변경을 다시 적용하면서 부모 등 커밋 정보가 달라지기 때문입니다.

충돌 표시만 지우면 끝인가요?

아닙니다. 두 변경의 의도를 반영한 결과인지 확인한 뒤 add하고 통합을 완료합니다. 코드라면 테스트도 합니다.
