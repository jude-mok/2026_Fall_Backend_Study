REST API 처음부터 설계하기

REST API가 무엇인지부터 시작합니다. 요청 하나의 전체 흐름을 먼저 보고, 각 부분을 자세히 살펴봅니다. 실습은 main.py 파일 하나를 기준으로 진행합니다. Client와 server, HTTP의 기초 흐름은 이전 주차에서 배운 내용으로 연결합니다.

1. REST API란 무엇인가?

REST API는 REST라는 설계 원칙에 따라 만든 API입니다. 먼저 API와 REST를 나누어 이해해 봅시다.

API는 다른 프로그램의 기능을 정해진 방식으로 사용할 수 있게 하는 접점입니다. 이 수업에서는 HTTP로 요청하고 응답받는 API를 다룹니다. 사용자는 정보를 조회하거나 수정할 수 있습니다. API는 이를 어떤 요청으로 표현할지 정합니다.

REST는 Representational State Transfer의 약자입니다. 네트워크로 연결된 프로그램의 상호작용을 정하는 설계 방식입니다. 먼저 REST의 핵심 개념인 resource부터 살펴봅니다. 나머지 설계 제약은 10절에서 설명합니다.

Resource는 API가 식별하여 다루는 대상입니다. 사용자 한 명, 게시글 한 개, 주문 한 건이 resource가 될 수 있습니다.

“42번 사용자를 조회한다”라는 요구사항을 생각해 봅시다. 대상은 42번 사용자입니다. 요청하는 동작은 조회입니다. 이 두 부분을 다음처럼 표현할 수 있습니다.

GET /users/42
  • /users/42는 어떤 대상인지 나타내는 주소의 경로입니다. 여기서는 42번 사용자입니다.
  • GET은 그 대상의 정보를 읽겠다는 요청입니다.
  • GET처럼 요청의 동작 의미를 나타내는 단어를 HTTP method라고 합니다.

대상은 주소로 식별하고, 요청하는 동작은 HTTP method로 나타냅니다. 다만 이 규칙만 지켰다고 REST의 모든 제약을 만족하는 것은 아닙니다. JSON 사용이나 복수형 URL도 그 자체로 REST의 필수 조건은 아닙니다.

REST의 정의와 제약: Fielding, chapter 5. HTTP method의 의미: RFC 9110 §9.

확인: “17번 게시글을 조회한다”에서 resource는 무엇일까요?

17번 게시글입니다. 조회는 그 resource에 대해 요청하는 동작입니다. 예를 들어 GET /posts/17로 표현할 수 있습니다.

2. 전체 그림: 요구사항에서 요청·응답까지

세부 문법에 들어가기 전에 API 하나가 어떻게 연결되는지 봅시다. 이번 목표는 “42번 사용자의 이름을 화면에 표시한다”입니다.

Path는 주소에서 요청 대상을 가리키는 경로입니다. Endpoint는 이 수업에서 method와 path의 조합을 뜻합니다. Status code는 처리 결과를 나타내는 숫자입니다. Body는 메시지에 담는 실제 내용입니다. JSON은 데이터를 텍스트로 표현하는 형식입니다. JSON의 기호는 다음 절에서 설명합니다.

요구사항
42번 사용자 조회
Request
GET /users/42
main.py
연결된 함수 실행
Response
200 + 사용자 데이터
  1. 대상을 정합니다. 대상은 42번 사용자입니다.
  2. Endpoint를 정합니다. 이 예제에서는 GET /users/42입니다.
  3. Server가 요청을 받으면 main.py에 정의한 함수를 실행합니다. 함수는 정해진 작업을 수행하는 코드 묶음입니다.
  4. 함수가 사용자 데이터를 반환합니다. 여기서 반환은 처리한 값을 돌려주는 것입니다.
  5. Server는 성공을 뜻하는 status code 200과 사용자 JSON을 응답합니다.
  6. Client가 응답에서 이름을 읽고 화면에 표시합니다.
요청: GET /users/42

응답 status code: 200
응답 body: {"id": "42", "name": "Ada"}

응답 body는 식별값이 42이고 이름이 Ada라는 정보를 나타냅니다. 이 데이터는 지금은 main.py에 직접 적어도 됩니다. Database는 데이터를 저장하고 조회하는 시스템입니다. 이번 실습에서는 database 없이 요청과 응답의 연결부터 확인합니다.

Contract는 API를 사용하는 쪽과 제공하는 쪽이 지킬 규칙입니다. “사용자를 조회한다”뿐 아니라 요청 주소, 입력, 성공 응답, 실패 응답까지 포함합니다.

전체 그림의 부분이 예제에서 정한 규칙자세히 볼 곳
대상과 데이터 표현42번 사용자 정보를 JSON으로 제공3~4절
주소와 입력식별값을 /users/42에 넣음5절
동작과 반복 효과GET으로 정보를 읽음6~7절
성공과 실패성공하면 200, 사용자가 없으면 4048절
다른 동작으로 확장생성·수정·삭제의 요청과 응답 설계9절
설계의 제약과 확장REST 제약, 목록 크기, 변경 정책 확인10~12절
직접 확인main.py 하나에서 조회 요청 실행13절

오늘의 구현 범위는 main.py 하나에서 조회 요청과 JSON 응답을 연결하는 것입니다. 생성·수정·삭제는 먼저 요청과 응답을 설계합니다. 전체 CRUD 구현과 파일 분리는 이후 학습으로 이어갑니다.

확인: main.py 내부 코드를 바꿔도 API를 사용하는 쪽이 그대로 동작하려면 무엇을 유지해야 할까요?

외부 contract를 유지해야 합니다. 요청 방법과 입력 규칙, 응답의 형태와 의미가 계속 같아야 합니다. 내부 코드가 같은 파일에 있는지는 client가 의존할 규칙이 아닙니다.

3. JSON: 데이터를 어떻게 읽는가?

JSON은 데이터를 텍스트로 표현하는 형식입니다. JavaScript Object Notation의 약자입니다. 이름에 JavaScript가 있지만 Python 등 다른 언어에서도 사용합니다. 아래 예시는 사용자 한 명의 정보입니다.

{
  "id": "usr_42",
  "name": "Ada",
  "age": 20,
  "active": true
}
  • { }는 이름과 값의 묶음인 object를 나타냅니다.
  • "name"은 값의 이름인 key입니다. "Ada"는 그 이름에 대응하는 value입니다.
  • :은 key와 value를 나눕니다. ,는 서로 다른 항목을 나눕니다.
  • "Ada"처럼 따옴표로 감싼 값은 string입니다. 글자로 된 데이터입니다.
  • 20은 숫자입니다. "20"은 글자이므로 다른 종류의 값입니다.
  • true와 false는 참과 거짓을 나타내는 boolean입니다.
  • id는 이 예제에서 사용자를 구별하는 식별값입니다. usr_42는 임의로 정한 값입니다.

Field는 데이터의 한 항목을 뜻합니다. 예를 들어 name field의 값은 Ada입니다. [ ]는 여러 값을 순서대로 넣는 array입니다. []는 값이 없는 array입니다. null은 값이 없음을 명시하는 JSON 값입니다. Field 자체가 빠진 것과 같은 의미인지는 API가 정해야 합니다.

{
  "items": [
    {"id": "usr_42", "name": "Ada"},
    {"id": "usr_43", "name": "Lin"}
  ],
  "nextCursor": null
}

items에는 사용자 두 명이 들어 있습니다. nextCursor는 뒤에서 설명할 다음 페이지 정보입니다. 이 예제에서는 null이므로 다음 페이지가 없다는 약속입니다. JSON 문법 자체가 이 의미를 정하는 것은 아닙니다.

형식 근거: RFC 8259, JSON.

확인: {"age": 20}과 {"age": "20"}은 같은 입력일까요?

아니요. 첫 번째 값은 숫자이고 두 번째 값은 string입니다. Server가 둘 다 허용할지는 입력 규칙에 달려 있습니다.

4. Resource와 representation

Resource는 API가 식별하여 다루는 대상입니다. 사용자 한 명, 사용자 목록, 주문 한 건이 resource가 될 수 있습니다. Resource를 설계할 때는 “client가 무엇을 필요로 하는가?”부터 확인합니다.

Representation은 resource의 상태를 전달하는 데이터 표현입니다. “Ada라는 사용자”가 resource라면, 이름과 식별값을 담은 JSON은 그 사용자의 representation입니다. JSON만 가능한 것은 아닙니다.

사용자 한 명의 주소를 /users/usr_42로 정해 봅시다. users는 사용자 목록을 가리키는 이름입니다. usr_42는 특정 사용자를 고릅니다. 이 주소가 반드시 database의 파일 위치나 table 이름과 일치할 필요는 없습니다. Table은 database에서 데이터를 행과 열로 정리한 구조입니다.

예를 들어 database는 이름과 내부 운영 메모를 함께 저장할 수 있습니다. 사용자 목록 화면은 이름만 필요할 수 있습니다. 그러면 응답에는 식별값과 이름만 포함하도록 설계할 수 있습니다. 비밀번호나 내부 보안 정보는 공개 응답에 넣지 않습니다.

확인: Database의 모든 열을 JSON으로 보내야 resource를 정확히 표현한 것일까요?

아니요. Representation은 이 API가 공개하기로 한 정보를 담습니다. 저장된 모든 정보를 복사할 필요는 없습니다. Client가 필요로 하는 정보와 공개 권한을 기준으로 결정합니다.

5. URL과 요청의 네 가지 입력 위치

URL은 요청할 대상을 가리키는 주소입니다. 아래 주소를 왼쪽부터 나누어 읽어 봅시다.

https://api.example.com/users/usr_42?include=profile
부분의미
https://HTTPS로 통신합니다.
api.example.com요청할 서버의 이름입니다. 예시용 주소입니다.
/users/usr_42Path입니다. 서버 안에서 요청 대상을 가리킵니다.
?include=profileQuery입니다. 여기서는 profile 정보를 함께 달라는 조건입니다.

Parameter는 요청할 때 값을 넣는 항목입니다. Path parameter는 path의 일부분을 바꾸어 넣는 값입니다. 문서의 /users/{id}에서 {id}는 실제 식별값이 들어갈 자리입니다. 실제 요청에서는 /users/usr_42처럼 보냅니다.

Query parameter는 물음표 뒤의 이름과 값입니다. limit=20은 limit이라는 항목에 20을 넣은 것입니다. 여러 조건은 &로 연결합니다. 예를 들어 /users?role=admin&limit=20은 admin 역할의 사용자를 최대 20명 달라는 설계입니다.

Header는 메시지의 형식이나 인증 정보 등을 전달하는 항목입니다. Body는 생성할 사용자 정보처럼 실제로 전달할 내용을 담는 부분입니다. Header와 body는 요청뿐 아니라 응답에도 사용합니다.

위치이 수업의 사용 기준예시
Path어떤 대상인가?/users/usr_42
Query어떤 조회 조건인가??limit=20
Header내용의 형식 등 부가 정보Content-Type: application/json
Body보낼 데이터{"name": "Ada"}

Content-Type: application/json은 “이 메시지의 body가 JSON이다”라는 뜻입니다. Accept: application/json은 “JSON 응답을 받을 수 있다”라는 뜻입니다. 둘은 가리키는 방향이 다릅니다.

Authentication은 요청자의 신원을 확인하는 과정입니다. Token은 인증에 사용할 수 있는 값입니다. 일부 API는 Authorization header로 token을 받습니다. 비밀번호나 token을 URL에 넣으면 방문 기록이나 로그에 남기 쉽습니다. Body에 넣는 것만으로 암호화되지는 않으므로 HTTPS도 필요합니다.

확인: usr_42의 이름을 바꿀 때, 대상 식별값과 새 이름은 각각 어디에 둘까요?

이 수업에서는 식별값을 path에 둡니다. 새 이름은 body에 둡니다. 예를 들어 대상은 /users/usr_42이고 body는 {"name": "Grace"}입니다.

6. HTTP method와 CRUD

HTTP method는 요청의 동작 의미를 나타내는 단어입니다. 같은 path라도 method가 다르면 다른 요청입니다. 이 수업에서는 method와 path의 조합을 endpoint라고 부릅니다.

CRUD는 Create, Read, Update, Delete의 첫 글자입니다. 각각 만들기, 읽기, 수정하기, 삭제하기입니다. HTTP의 모든 동작이 CRUD에만 속하는 것은 아닙니다.

목적예시 endpoint의미
목록 읽기GET /users목록 representation 요청
한 명 읽기GET /users/usr_42특정 사용자 representation 요청
새 사용자 만들기POST /users이 API에서 정의한 생성 처리 요청
전체 교체PUT /users/usr_42지정한 대상 상태를 제공한 표현으로 교체
부분 변경PATCH /users/usr_42제공한 변경 내용 적용
삭제DELETE /users/usr_42대상의 삭제 요청

/users처럼 명사와 복수형을 쓰는 것은 널리 쓰이는 설계 관례입니다. REST의 필수 문법은 아닙니다. GET /deleteUser처럼 읽기 요청으로 삭제하게 설계하면 GET의 의미에 어긋납니다.

PUT과 PATCH를 같은 데이터로 비교하기

이 예제에서는 client가 설정할 수 있는 사용자 field를 name과 email 두 개로 정합니다. 현재 name은 Ada이고 email은 ada@example.com입니다.

현재 상태
{"name": "Ada", "email": "ada@example.com"}

PUT /users/usr_42
{"name": "Grace", "email": "grace@example.com"}

교체 후
{"name": "Grace", "email": "grace@example.com"}

PUT에서는 교체할 전체 표현을 보냅니다. Server가 관리하는 id까지 반드시 보내야 한다는 뜻은 아닙니다. 이 예제의 PUT은 name과 email을 모두 요구합니다. 하나를 빠뜨리면 오류로 처리한다고 정합니다. 빠진 field를 몰래 유지하는 방식은 여기서 사용하는 전체 교체 규칙과 맞지 않습니다.

현재 상태
{"name": "Ada", "email": "ada@example.com"}

PATCH /users/usr_42
{"name": "Grace"}

변경 후
{"name": "Grace", "email": "ada@example.com"}

이 예제의 PATCH는 보낸 field만 바꾸고 나머지는 유지한다고 정했습니다. PATCH라는 단어만으로 JSON의 해석 규칙이 결정되지는 않습니다. 지원하는 body 형식, 빠진 field의 처리, null의 처리를 문서에 써야 합니다.

POST는 생성에만 사용할 수 있는 method가 아닙니다. 대상 API에 정의된 처리를 요청할 수 있습니다. PUT도 API가 허용하면 지정한 주소에 새 resource를 만들 수 있습니다.

동작의 근거: RFC 9110 §9, RFC 5789 §2. Field 구성은 이 수업의 예제 정책입니다.

확인: 사용자의 이름만 바꾸고 email은 유지하려면 이 예제에서는 무엇을 보낼까요?

PATCH /users/usr_42에 {"name": "Grace"}를 보냅니다. 이름 변경이라는 요구가 부분 변경 규칙과 맞기 때문입니다.

7. Safe와 idempotent: 요청을 반복하면?

Client가 요청을 보낸 뒤 응답을 받지 못할 수 있습니다. 이때 요청이 실패했는지, 처리는 끝났지만 응답만 사라졌는지 바로 알 수 없습니다. 그래서 같은 요청을 다시 보내도 되는지 생각해야 합니다.

Safe는 client가 요청한 동작이 서버 상태의 변경을 요구하지 않는다는 성질입니다. GET이 대표적입니다. Server가 접속 로그를 기록하는 것까지 금지한다는 뜻은 아닙니다.

Idempotent는 동일한 요청을 여러 번 처리해도, 의도한 서버 상태의 효과가 한 번 처리한 것과 같다는 성질입니다. 응답 내용이나 status code가 매번 같다는 뜻은 아닙니다.

  1. 사용자 usr_42를 삭제합니다. 삭제 후에는 사용자가 없습니다.
  2. 같은 사용자를 다시 삭제하려고 합니다. 여전히 사용자가 없습니다.
  3. 첫 응답은 성공이고 두 번째 응답은 “없음”일 수 있습니다. 그래도 의도한 최종 상태는 같습니다.
MethodSafeIdempotent
GET예예
POST아니요보장하지 않음
PUT아니요예
PATCH아니요보장하지 않음
DELETE아니요예

“name을 Grace로 설정”하는 PATCH는 반복해도 같은 값이 됩니다. 반면 “점수를 1 올림”이라는 변경 규칙은 반복할 때마다 점수가 증가합니다. PATCH의 반복 효과는 실제 변경 규칙에 달려 있습니다.

근거: RFC 9110 §9.2, RFC 5789 §2.

확인: POST /users의 응답이 오지 않았습니다. 같은 요청을 바로 반복하면 항상 안전할까요?

아니요. 첫 생성이 이미 끝났을 수 있습니다. 중복 요청을 구별하는 별도의 규칙이 없다면 또 생성될 수 있습니다. 실제 결과는 중복 email 제한 등 API 정책에도 달려 있습니다.

8. Status code와 오류 응답

Status code는 response의 처리 결과를 나타내는 세 자리 숫자입니다. 첫 자리로 큰 범주를 구별합니다. 2xx의 xx는 나머지 두 자리를 뜻합니다.

범주의미
1xx처리 도중의 정보
2xx성공
3xx다른 위치 사용 등 추가 조치
4xx요청을 처리할 수 없는 client 측 조건
5xxServer 측 처리 실패

아래 표의 상황은 이번 사용자 API에서 정한 예시입니다. 모든 API가 같은 입력 오류에 반드시 같은 code를 쓰는 것은 아닙니다.

Code이름예시
200OK사용자 조회 성공, body에 결과 포함
201Created새 사용자 생성 완료
204No Content삭제 완료, 응답 body 없음
400Bad RequestJSON 문법이 깨진 요청
401Unauthorized유효한 인증 정보 없음
403Forbidden작업을 허용하지 않음
404Not Found요청한 사용자 없음
409Conflict이미 등록된 email과 충돌
422Unprocessable ContentJSON은 읽었지만 email 값이 입력 규칙에 맞지 않음
500Internal Server Error예상하지 못한 내부 처리 실패

401은 WWW-Authenticate header로 인증 방식 안내를 포함해야 합니다. 403은 반드시 “로그인한 사람”에게만 사용하는 code는 아닙니다. 여기서는 인증된 사용자가 다른 사람의 정보를 수정하려는 경우를 예로 듭니다.

Authorization은 해당 작업을 허용할지 확인하는 과정입니다. Authentication으로 누군지 확인했어도, 모든 작업을 허용하는 것은 아닙니다.

사람과 프로그램이 모두 처리할 수 있는 오류

Validation은 입력이 정한 규칙을 만족하는지 검사하는 과정입니다. 예를 들어 email에 필요한 형식이 있는지 확인합니다. 아래 오류 모양은 이번 수업의 자체 규칙입니다.

{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Email format is invalid",
    "details": [
      {"field": "email", "reason": "invalid_format"}
    ]
  }
}
  1. Client는 HTTP status code 422로 입력 관련 실패임을 확인합니다.
  2. error.code로 처리할 오류 종류를 고릅니다.
  3. details의 field를 읽고 email 입력칸을 표시합니다.
  4. 사용자에게 email을 고치라는 안내를 보여줍니다.

message는 설명 문장입니다. 번역이나 표현 변경으로 바뀔 수 있습니다. Client의 처리 조건을 message 문장과의 일치 여부로 만들지 않습니다. Code와 details의 의미를 안정적으로 유지합니다.

내부 실행 경로나 database 명령 전체를 오류 응답에 넣지 않습니다. 개발용 진단 정보는 server 쪽에 기록하고, client에는 필요한 안내를 보냅니다.

Status 의미의 근거: RFC 9110 §15. 표의 상황과 오류 JSON은 이 수업에서 선택한 정책입니다.

확인: GET /users 결과가 빈 목록이면 반드시 404일까요?

아니요. 목록 resource가 있고 구성원만 없다면 200과 {"items": []}를 돌려줄 수 있습니다. 특정 사용자를 찾지 못한 상황과 구별합니다.

9. 사용자 생성부터 삭제까지 추적하기

지금부터 같은 사용자 usr_42를 계속 사용합니다. HTTP/1.1은 예시에 사용한 HTTP 버전 표시입니다. Host는 요청할 서버 이름입니다. Location은 새로 만든 resource의 주소를 알려주는 response header입니다.

① Create: 사용자 만들기

POST /users HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json

{"name":"Ada","email":"ada@example.com"}
  1. POST로 사용자 생성 처리를 요청합니다.
  2. /users는 사용자를 추가할 목록입니다.
  3. Content-Type은 보내는 body의 형식을 알려줍니다.
  4. 빈 줄 뒤의 body에 이름과 email을 넣습니다.
  5. Server는 입력과 email 중복을 검사합니다.
  6. Server는 새 사용자를 저장하고 식별값 usr_42를 부여합니다.
HTTP/1.1 201 Created
Location: /users/usr_42
Content-Type: application/json

{"id":"usr_42","name":"Ada","email":"ada@example.com"}

201은 생성 완료를 나타냅니다. Location으로 새 주소를 알려줍니다. Body에는 이 client에게 제공하기로 한 사용자 정보를 담습니다.

② Read: 만든 사용자 읽기

GET /users/usr_42 HTTP/1.1
Host: api.example.com
Accept: application/json
HTTP/1.1 200 OK
Content-Type: application/json

{"id":"usr_42","name":"Ada","email":"ada@example.com"}

Client는 생성 응답에서 받은 식별값을 path에 넣습니다. 이 GET 요청에는 body가 필요하지 않습니다. 일반적인 조회 조건은 query로 보냅니다.

③ Update: 이름만 바꾸기

이 API는 application/json 형식의 자체 PATCH 규칙을 사용합니다. name과 email만 수정할 수 있습니다. 빠진 field는 유지합니다. null은 허용하지 않습니다.

PATCH /users/usr_42 HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"name":"Grace"}
HTTP/1.1 200 OK
Content-Type: application/json

{"id":"usr_42","name":"Grace","email":"ada@example.com"}

이름은 바뀌었습니다. Email은 그대로입니다. 수정한 결과를 body에 담기로 했으므로 200을 사용합니다. Body를 보내지 않는 정책이라면 204를 사용할 수 있습니다.

④ Delete: 사용자 삭제하기

DELETE /users/usr_42 HTTP/1.1
Host: api.example.com
HTTP/1.1 204 No Content

204 뒤에는 JSON body를 붙이지 않습니다. 이 API에서는 삭제한 사용자를 다시 조회하면 404를 돌려줍니다. 실제 저장 기록을 언제 지울지는 별도의 내부 정책입니다.

확인: 204 응답에 {"success": true}를 함께 보내도 될까요?

안 됩니다. 204는 응답 내용이 없다는 뜻입니다. 성공 데이터를 body로 보내려면 200 등 목적에 맞는 응답을 선택합니다.

10. REST가 요구하는 설계 제약

REST는 Representational State Transfer의 약자입니다. 네트워크로 연결된 시스템의 구성과 상호작용을 제한하는 설계 방식입니다. 이러한 설계 방식을 architectural style이라고 부릅니다.

HTTP API는 HTTP로 기능을 제공하는 API입니다. 그중 REST 제약에 따라 설계한 API를 REST API라고 부릅니다. URL에 명사를 쓰고 JSON을 보낸다는 사실만으로 모든 REST 제약을 만족하지는 않습니다.

먼저 필요한 용어를 정의합니다. Cache는 나중에 재사용하려고 저장한 응답입니다. Layer는 통신을 처리하는 중간 단계입니다. Interface는 외부에서 기능을 사용하는 방식입니다.

제약의미
Client–server화면을 사용하는 쪽과 요청을 처리하는 쪽의 책임을 분리합니다.
Stateless각 요청에 처리에 필요한 정보를 담습니다. 이전 요청의 대화 상태를 서버가 기억해야만 해석되는 요청을 피합니다.
Cache응답을 재사용할 수 있는지 알 수 있게 합니다.
Uniform interfaceResource 식별과 representation 사용 등 공통된 상호작용 규칙을 사용합니다.
Layered systemClient는 직접 연결한 단계 뒤의 모든 내부 구성을 알 필요가 없습니다.
Code-on-demandClient가 실행할 코드를 제공할 수 있습니다. 선택적인 제약입니다.

Stateless는 database를 없애라는 뜻이 아닙니다

“아까 말한 사용자의 이름을 바꿔 줘”라는 요청은 이전 대화를 알아야 이해할 수 있습니다. 반면 “usr_42의 이름을 Grace로 바꿔 줘”라는 요청은 대상을 포함합니다. 필요한 인증 정보도 각 요청에 포함하도록 설계합니다. 저장된 사용자 데이터가 존재하는 것과 요청 사이의 대화 상태에 의존하는 것은 다릅니다.

심화: Uniform interface에는 무엇이 더 포함될까요?

원래 REST는 resource 식별, representation을 통한 조작, 스스로 해석에 필요한 정보를 담은 메시지, hypermedia로 다음 동작을 안내하는 것을 요구합니다.

Hypermedia는 데이터에 링크나 다음 동작을 안내하는 정보를 포함하는 방식입니다. 예를 들어 응답이 다음 페이지 주소를 제공하면 client가 그 주소를 따라갈 수 있습니다. 링크 하나를 넣었다고 모든 REST 제약을 충족하는 것은 아닙니다.

실무에서 REST API라고 부르는 API 중에는 이러한 제약을 일부만 적용한 API도 있습니다. 이번 수업의 CRUD 예제는 resource 중심 HTTP API 설계를 연습하기 위한 것입니다. 완전한 REST 시스템 구현을 주장하지 않습니다.

원전: Roy Fielding, dissertation chapter 5.

확인: Server가 사용자 정보를 database에 저장하면 stateless를 위반할까요?

아니요. Resource의 데이터를 저장할 수 있습니다. Stateless는 각 요청을 처리하기 위해 이전 대화 상태에 의존하는지를 다룹니다.

11. Pagination: 목록을 나누어 가져오기

사용자가 100만 명이면 전체 목록을 한 번에 보내는 데 많은 시간과 메모리가 필요합니다. Pagination은 목록을 일정한 크기로 나누어 가져오는 방식입니다. 한 번에 가져오는 묶음을 page라고 부릅니다.

Offset: 앞에서 몇 개를 건너뛸까?

Limit은 최대 몇 개를 가져올지 나타냅니다. Offset은 앞에서 몇 개를 건너뛸지 나타냅니다. 예제 목록의 순서는 A, B, C, D, E입니다. 각 글자는 사용자 한 명을 뜻합니다.

GET /users?limit=2&offset=0  → A, B
GET /users?limit=2&offset=2  → C, D
GET /users?limit=2&offset=4  → E

첫 요청은 0개를 건너뛰고 2개를 읽습니다. 두 번째 요청은 2개를 건너뛰고 다음 2개를 읽습니다. 이렇게 페이지의 위치를 숫자로 지정할 수 있습니다.

그런데 첫 요청 후 목록 맨 앞에 X가 추가되면 어떻게 될까요?

  1. 첫 요청에서 A, B를 받습니다.
  2. 목록이 X, A, B, C, D, E로 바뀝니다.
  3. Offset 2는 이제 X와 A를 건너뜁니다.
  4. 두 번째 요청에서 B, C를 받습니다. B가 중복됩니다.

첫 페이지의 항목이 삭제되면 다음 페이지의 항목을 건너뛸 수도 있습니다. 또한 database가 큰 offset만큼 건너뛸 데이터를 처리해야 하면 느려질 수 있습니다. 결과를 정렬하는 기준도 항상 정해야 합니다.

Database의 LIMIT/OFFSET 동작: PostgreSQL documentation §7.6. A–E 변화는 원리를 설명하기 위한 예시입니다.

Cursor: 어느 항목 다음부터 가져올까?

Cursor는 다음 조회를 시작할 위치를 나타내는 값입니다. 아래 예제에서는 server가 B 다음 위치를 after_B라는 값으로 표현했다고 가정합니다. 실제 API에서는 이 값을 client가 해석하지 않고 그대로 돌려보내도록 만들 수 있습니다.

{
  "items": [{"id": "A"}, {"id": "B"}],
  "nextCursor": "after_B"
}
GET /users?limit=2&cursor=after_B  → C, D

Client는 첫 응답의 nextCursor를 다음 요청의 cursor에 넣습니다. 목록 앞에 X가 추가되어도 “B 다음”이라는 기준을 사용합니다. 이 예제에서는 C, D를 계속 가져옵니다.

Cursor도 모든 중복과 누락을 자동으로 없애지는 않습니다. 정렬 기준 값이 바뀌거나 항목이 삭제되는 상황의 처리 정책이 필요합니다. 같은 정렬 값이 여러 개라면 식별값 등 추가 기준으로 순서를 확정해야 합니다.

정할 정책예제
기본 page 크기20개
최대 page 크기100개. 초과 입력은 422
정렬 기준생성 시각 순서. 같으면 식별값 순서
마지막 page 표시nextCursor가 null
잘못된 cursor400과 INVALID_CURSOR 오류
확인: nextCursor가 null인 응답을 받으면 client는 무엇을 해야 할까요?

이 API의 정책에서는 다음 페이지가 없으므로 추가 조회를 멈춥니다. 예를 들어 “더 보기” 버튼을 비활성화할 수 있습니다.

12. Compatibility와 versioning

Backward compatibility는 API를 변경해도 기존 client가 계속 동작하는 성질입니다. 모든 사용자가 같은 날 앱을 업데이트한다고 가정하면 안 됩니다.

기존 응답: {"id": "usr_42", "name": "Ada"}
변경 응답: {"id": "usr_42", "displayName": "Ada"}

기존 client가 name을 읽는다면 변경 후 값을 찾지 못합니다. 이처럼 기존 동작을 깨뜨리는 변경을 breaking change라고 합니다.

변경영향
응답에 선택적인 field 추가Client가 모르는 field를 무시하면 대체로 호환됩니다.
name 삭제 또는 이름 변경name을 사용하는 client가 실패합니다.
숫자를 string으로 변경숫자 계산이나 입력 검사가 실패할 수 있습니다.
요청에 필수 field 추가이 값을 보내지 않던 client가 실패합니다.
같은 field의 단위 변경Code가 실행되어도 잘못된 값을 계산할 수 있습니다.

Versioning은 API의 서로 다른 계약을 구별하는 방식입니다. 예를 들어 /v1/users와 /v2/users를 사용할 수 있습니다. Version 숫자를 추가한다고 기존 client가 자동으로 고쳐지지는 않습니다.

  1. 무엇이 바뀌는지 문서화합니다.
  2. 기존 version의 지원 기간을 정합니다.
  3. Client가 새 version으로 바꾸는 방법을 안내합니다.
  4. 지원 기간 동안 기존 요청이 계속 동작하는지 확인합니다.
확인: 응답 field 추가는 언제나 호환될까요?

언제나는 아닙니다. 알 수 없는 field가 있으면 거부하는 client도 있을 수 있습니다. Client의 처리 방식과 합의한 계약을 확인해야 합니다.

13. 직접 설계하고 설명하기

먼저 문제를 풀고 해설을 여세요. 정답 문자열을 외우기보다 대상, 동작, 입력, 결과를 각각 설명하는 것이 목표입니다.

실행 실습 — main.py 하나에서 전체 흐름 확인

FastAPI는 Python으로 HTTP 요청을 처리하고 응답하는 프로그램을 만들도록 돕는 도구입니다. 현재 수업은 FastAPI를 설치하고 main.py를 실행할 수 있는 상태에서 시작합니다. 아래는 독립적으로 실행할 수 있는 최소 예제입니다. 기존 main.py가 있다면 app 생성은 그대로 두고, 같은 경로가 없는지 확인한 뒤 조회 함수를 추가하세요.

코드를 읽기 전에 문법을 확인합니다. from ... import ...는 사용할 기능을 가져옵니다. =는 오른쪽 값을 왼쪽 이름에 저장합니다. FastAPI()는 요청을 처리할 앱을 만듭니다. @app.get(...)은 GET 요청 경로를 바로 아래 함수에 연결합니다. def는 함수를 정의합니다. return은 함수의 결과를 돌려줍니다.

from fastapi import FastAPI

app = FastAPI()

@app.get("/users/42")
def read_user():
    return {"id": "42", "name": "Ada"}

read_user는 함수 이름입니다. 괄호가 비어 있으므로 여기서는 입력을 받지 않습니다. 함수 정의 끝의 : 다음에는 들여쓴 실행 코드가 옵니다. 마지막 줄의 중괄호는 Python의 dictionary입니다. 이름과 값을 묶는 자료 구조입니다. FastAPI가 이 값을 JSON 응답으로 변환합니다.

  1. 위 코드를 실습용 main.py에 저장합니다.
  2. main.py가 있는 폴더에서 아래 명령을 실행합니다.
  3. 브라우저에서 아래 조회 주소를 엽니다.
  4. 응답에 id와 name이 나오는지 확인합니다.
uv run fastapi dev main.py

uv run은 프로젝트 환경에서 명령을 실행합니다. fastapi dev는 개발용 server를 실행합니다. 마지막 main.py는 실행할 파일입니다. 기존 수업 프로젝트처럼 app 폴더 안에 파일이 있으면 프로젝트 폴더에서 uv run fastapi dev app/main.py를 사용합니다.

http://127.0.0.1:8000/users/42

127.0.0.1은 현재 컴퓨터를 가리킵니다. 8000은 이 개발용 server가 요청을 받는 port 번호입니다. Port는 같은 컴퓨터의 여러 통신 접점을 구분하는 번호입니다. 브라우저 주소창으로 이 주소를 열면 GET 요청을 보냅니다.

이 예제는 항상 같은 사용자 정보를 돌려줍니다. 사용자를 저장하거나 검색하는 코드는 아직 없습니다. /users/43은 별도로 정의하지 않았으므로 404 응답을 받습니다. 이후에는 path parameter를 사용하여 여러 식별값을 처리할 수 있습니다.

실행 후 확인: Ada를 Grace로 바꾸면 무엇이 달라질까요?

함수가 돌려주는 name 값이 바뀝니다. 저장 후 개발 server가 다시 준비되면 같은 주소를 새로 조회하세요. Endpoint는 그대로이고 response의 데이터가 달라집니다. 이것은 PATCH 요청을 구현한 것이 아니라, 예제 코드에 적힌 값을 직접 바꾼 것입니다.

설계 실습으로 확장하기

아래 실습은 코드를 추가하는 과제가 아니라 요청·응답 규칙을 작성하는 과제입니다. main.py에서 확인한 흐름을 생성·수정·삭제까지 확장해 봅니다.

실습 1 — 사용자 API 명세 작성

명세는 API의 사용 규칙을 적은 문서입니다. 아래 요구사항을 읽고 각 요청의 method, path, 입력, 성공 응답, 실패 응답을 정하세요.

  • 사용자 생성에는 name과 email이 필요합니다.
  • Name은 앞뒤 공백 제거 후 1~50글자여야 합니다.
  • Email은 유효한 형식이어야 하며 중복되면 안 됩니다.
  • 이름만 수정할 수 있어야 합니다.
  • 존재하지 않는 사용자를 조회하면 실패를 알려야 합니다.
  • 목록은 한 번에 최대 100개까지만 조회할 수 있습니다.
해설: 가능한 명세 예시
Endpoint입력성공실패
POST /usersBody: name, email201, 사용자 JSON, Location400 잘못된 JSON / 422 입력 규칙 위반 / 409 email 중복
GET /users/{id}Path: id200, 사용자 JSON404 사용자 없음
PATCH /users/{id}Path: id, body: name200, 변경한 사용자 JSON404 사용자 없음 / 422 이름 오류
GET /usersQuery: limit, cursor200, items와 nextCursor422 limit 오류 / 400 cursor 오류
DELETE /users/{id}Path: id204, body 없음404 사용자 없음

여기서는 기본 limit을 20, 허용 범위를 1~100으로 정합니다. 성공 응답의 field와 정렬 기준도 앞의 예제를 따릅니다. 실제 서비스라면 인증 요구 여부와 field별 공개 범위도 명세에 추가해야 합니다.

실습 2 — 실패 네 가지 구분

잘못된 JSON, 잘못된 email 형식, 중복 email, 없는 사용자 조회에 각각 HTTP status와 error.code를 배정하세요.

해설: 이번 수업의 정책
  • 400 / INVALID_JSON: 데이터를 JSON으로 읽을 수 없습니다.
  • 422 / VALIDATION_ERROR: JSON은 읽었지만 값이 규칙에 맞지 않습니다.
  • 409 / EMAIL_ALREADY_EXISTS: 기존 사용자 정보와 충돌합니다.
  • 404 / USER_NOT_FOUND: 지정한 사용자가 없습니다.

error.code의 문자열은 HTTP 표준이 정한 값이 아닙니다. 팀에서 정한 규칙입니다. Client와 공유하고 일관되게 유지해야 합니다.

실습 3 — API와 database 구조 분리

Database의 모든 열을 응답에 복사하면 어떤 문제가 생길까요? 두 가지를 설명하세요.

해설

첫째, 내부 정보나 민감한 정보가 노출될 수 있습니다. 둘째, database 구조를 바꿀 때 client까지 바꿔야 할 수 있습니다. 공개할 field를 별도로 정의하면 내부 저장 방식과 외부 계약을 분리하기 쉬워집니다.

실습 4 — 로그인 동작 설계

Session은 로그인 상태를 관리하는 맥락에서 사용하는 개념입니다. 로그인 결과로 session resource를 만든다고 설계할 수 있습니다. POST /sessions와 POST /login 중 하나를 선택하고 그 이유를 설명하세요.

해설

POST /sessions는 “로그인 session 만들기”로 모델링한 설계입니다. POST /login은 “로그인 처리”를 직접 이름 붙인 설계입니다. 명사형 여부만으로 품질을 판정할 수 없습니다. 생성 결과와 종료 방법, 인증 규칙이 명확한지 확인해야 합니다. 서버에 저장된 대화 session에 의존하는 방식이 원래 REST의 stateless 제약을 만족하는지도 별도로 검토해야 합니다.
