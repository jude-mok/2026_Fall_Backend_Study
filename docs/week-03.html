수업 전 준비 · 각자의 repository¶

1·2주차에 만든 본인 GitHub repository를 이어서 사용한다. 아직 없다면 본인 계정에 새 repository를 만들고 로컬에 내려받는다. Python 3.13, uv, curl 설치와 아래 패키지 준비는 수업 시작 전에 완료한다. 수업은 설치가 끝난 상태를 기준으로 진행한다.

처음 준비하는 사람: 최소 서버 만들기

편집기에서 본인 repository 폴더를 열고 터미널을 연다. pyproject.toml은 Python 프로젝트의 설정 파일이다. 이 파일이 없을 때만 첫 명령을 실행하고, 두 번째 명령으로 FastAPI와 Uvicorn을 설치한다. FastAPI는 요청을 처리할 앱을 만드는 도구이고, Uvicorn은 연결을 받아 그 앱을 실행하는 서버다.

uv init --bare --python 3.13
uv add fastapi uvicorn

uv init --bare는 최소 설정을 만들고, uv add는 필요한 패키지를 설치하고 기록한다. uv.lock은 선택된 버전 기록, .venv는 프로젝트 전용 실행 환경이다. uv 공식 설명

app 폴더 안에 빈 __init__.py와 main.py를 만든다. __init__.py는 폴더를 Python package, 즉 코드 묶음으로 다룰 때 사용하는 파일이다. main.py에 아래 코드를 작성한다. 이미 /health가 있다면 기존 코드를 지우지 말고 해당 기능을 사용한다.

from fastapi import FastAPI

app = FastAPI()


@app.get("/health")
def health():
    return {"status": "ok"}

import는 사용할 도구를 가져온다. FastAPI()는 앱을 만들고, app =은 그 결과에 app이라는 이름을 붙인다. @app.get("/health")는 GET /health 요청을 바로 아래 함수에 연결한다. def health():는 health라는 함수를 정의한다. 함수는 호출될 때 정해진 일을 수행하는 코드 묶음이다.

return은 결과를 돌려준다. {"status": "ok"}는 이름과 값의 쌍을 담는 Python dictionary이며, FastAPI가 JSON으로 바꾸어 응답한다. 네 칸 들여쓴 return 줄은 함수 안에 속한다. 이번에는 이 코드를 통신 관찰 도구로 사용하고 FastAPI 문법은 6주차에서 자세히 배운다. FastAPI 공식 설명

내 서버에 접속하기¶

터미널 A에서 본인 repository의 최상위 폴더를 연 뒤 실행한다. --host는 서버가 기다릴 주소, --port는 기다릴 번호다. 이 창은 켜 둔다.

uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000

uv run은 이 프로젝트의 실행 환경에서 명령을 실행한다. uvicorn은 서버 실행 도구 이름이다. app.main:app에서 app.main은 app 폴더의 main.py 파일, 콜론 뒤 app은 그 파일 안의 app = FastAPI()로 만든 앱을 가리킨다. --reload는 코드를 수정하면 앱을 다시 불러오는 개발용 옵션이다.

실행 위치: 이번 개인 repo 예제에서는 app 폴더가 바로 보이는 최상위 폴더에서 실행한다. 본인 프로젝트가 backend/app/main.py 구조라면 먼저 cd backend로 backend 폴더로 이동한 뒤 같은 명령을 실행한다. 서버가 시작되면 터미널을 켜 두고, 요청은 별도의 터미널에서 보낸다.

브라우저에서 http://127.0.0.1:8000/health를 연다. 위 최소 서버라면 {"status":"ok"}가 보인다. 다른 필드를 추가했다면 응답이 달라도 된다. 오늘의 질문은 “이 주소의 숫자와 /health는 각각 무슨 일을 할까?”다.

서버 실행이 막히면 오류 메시지를 확인하고 진행자의 실행 결과를 함께 관찰한다. 환경 문제는 수업 후 해결하고 직접 다시 실행해 본다.

주소를 읽는 데 필요한 개념¶

Client와 server¶

Client는 요청을 시작하는 프로그램이다. 지금은 브라우저다. Server는 요청을 받아 처리하고 응답하는 프로그램이다. 지금은 실행한 FastAPI 앱이다. 서버 코드가 파일로 있어도 실행하지 않으면 응답할 수 없다.

HTTP는 요청과 응답의 형식과 의미를 정한 protocol이다. Protocol은 양쪽이 함께 지키는 통신 규칙이다. Client가 “/health를 보여 줘”라고 보내면 server가 결과와 성공 여부를 돌려준다. HTTPS는 이 HTTP 통신을 보호하며, 보호 방식은 다음 주에 배운다.

URL: 어디에 무엇을 요청하는가?¶

URL은 접근할 대상의 주소다. 실제 접속한 주소를 다음처럼 나눈다.

http://127.0.0.1:8000/health
부분뜻이 예에서
scheme접근 방식http
host접속 대상 이름 또는 IP address127.0.0.1: 내 컴퓨터
port같은 주소 안에서 통신할 창구를 구분하는 번호8000: 실행한 앱이 기다리는 곳
path서버에 요청할 대상의 경로/health: 상태 확인 기능

IP address는 network에서 사용하는 주소이고, DNS는 host 이름에 해당하는 주소 등을 찾는 체계다. https://example.com/처럼 이름으로 접속할 때 필요하다. 127.0.0.1을 직접 쓴 이번 요청에서는 외부 DNS 조회가 필요하지 않다.

localhost도 자기 기기를 가리키는 이름이다. 친구에게 이 주소를 보내면 친구의 컴퓨터를 가리킨다. Port를 생략하면 HTTP는 기본 80, HTTPS는 기본 443을 사용한다. 여기서는 8000을 명시했다. Path는 실제 폴더가 아니라 앱이 정한 기능일 수 있다.

선택 복습: query와 fragment

/health?week=3#summary에서 물음표 뒤 week=3은 추가 입력인 query다. # 뒤 summary는 문서 안 위치 등에 사용하는 fragment이며 HTTP 요청 대상에는 포함되지 않는다. 이번 최소 앱은 query를 사용하지 않으므로 응답은 그대로다. URL 구성 참고

DNS와 IP address: 접속할 주소 찾기¶

이름과 주소를 나누는 이유¶

Network는 기기들이 데이터를 주고받도록 연결된 구조다. IP address는 그 network에서 데이터를 보낼 때 사용하는 주소다. 사람은 숫자 주소보다 example.com 같은 이름을 기억하기 쉽다. 이런 이름을 domain name이라고 한다.

DNS는 Domain Name System의 줄임말로, 이름에 대한 정보를 조회하는 체계다. 웹 접속에서는 주로 host 이름을 사용해 IP address를 찾는다. 이름은 유지하면서 서버 주소를 바꿀 수도 있어서 이름과 주소를 따로 관리한다.

DNS 조회는 어떻게 진행될까?¶

https://example.com/에 처음 접속한다고 가정하자. Resolver는 주소 조회를 처리하는 역할이고, cache는 이전 조회 결과를 저장해 다시 쓰는 곳이다.

  1. 브라우저와 운영체제가 사용할 수 있는 저장된 주소 정보가 있는지 확인한다.
  2. 필요하면 설정된 DNS resolver에 example.com의 주소를 요청한다.
  3. Resolver는 자신의 cache 또는 다른 DNS 서버에서 답을 찾는다.
  4. Client는 받은 주소 중 사용할 주소로 연결을 시도한다. DNS 조회 성공과 서버 연결 성공은 서로 다른 단계다.

DNS는 /health를 처리할 함수를 찾지 않는다. Host 이름의 주소를 찾은 뒤, path를 처리하는 것은 HTTP 서버의 일이다. 127.0.0.1처럼 IP를 직접 쓴 로컬 요청에는 외부 DNS 조회가 필요하지 않다.

보충: resolver도 처음 보는 이름이라면?

Resolver는 root DNS 서버에서 시작해, .com 같은 top-level domain 담당 서버, 해당 domain의 authoritative name server로 안내받을 수 있다. Authoritative name server는 해당 domain의 정보를 제공할 책임이 있는 서버다. 모든 브라우저가 매번 이 과정을 직접 수행하는 것은 아니다. Cache에 필요한 정보가 있으면 일부 조회를 생략한다.

A record는 IPv4 주소, AAAA record는 IPv6 주소를 담는 DNS 항목이다. 두 이름은 IP 주소 형식의 종류이며 이번 수업에서는 표기법을 외울 필요는 없다. 한 이름이 여러 주소를 가질 수도 있다. TTL은 결과를 cache에 보관할 수 있는 시간을 나타내므로 DNS 정보를 바꿔도 이전 결과가 잠시 사용될 수 있다. DNS 개념 표준

이해 확인: “이름의 주소를 못 찾음”과 “주소는 찾았지만 서버에 연결하지 못함”을 구분할 수 있으면 된다.

Port와 TCP: 프로그램끼리 데이터 주고받기¶

같은 주소에서 어떤 프로그램을 찾을까?¶

하나의 컴퓨터에서 여러 서버 프로그램을 실행할 수 있다. Port는 같은 주소에서 통신 대상을 구분하는 숫자다. 예를 들어 FastAPI 앱은 8000, 다른 앱은 8001에서 요청을 기다리게 할 수 있다. 서버가 특정 주소와 port에서 연결 요청을 기다리는 것을 listen한다고 한다.

Process는 실행 중인 프로그램이다. 코드 파일을 저장한 것만으로는 서버 process가 생기지 않는다. 실행 명령으로 앱을 시작해야 listen할 수 있다. Client가 8000에 연결하는데 서버는 8001에서 기다린다면 서로 만나지 못한다.

TCP가 필요한 이유¶

Network에서 데이터는 작은 단위로 나뉘어 이동한다. 이때 전달하는 데이터 단위를 packet이라고 한다. 이동 중 일부가 사라지거나 도착 순서가 달라질 수 있다. IP는 주소에 따라 전달하는 역할을 하지만, 그 자체로 모든 데이터의 도착과 순서를 보장하지 않는다.

TCP는 Transmission Control Protocol의 줄임말이다. 양쪽 프로그램이 순서 있는 데이터 흐름을 주고받도록 관리한다. 예를 들어 전송한 데이터 중 앞부분이 빠지고 뒷부분이 먼저 도착하면, 누락을 확인해 필요한 데이터를 다시 보내고 원래 순서대로 전달하도록 관리한다.

TCP가 다루는 흐름을 byte stream이라고 한다. Byte는 데이터 크기를 세는 단위이고, stream은 이어지는 흐름이다. TCP는 이 흐름의 전달을 담당하고, “사용자 조회 요청인가?” 같은 메시지 의미는 HTTP가 해석한다. 연결이 끊기거나 일정 시간 동안 응답이 없으면 TCP도 결국 실패할 수 있다.

보충: three-way handshake로 연결 준비하기

Handshake는 통신 전에 양쪽의 상태를 맞추는 절차다. 일반적인 새 TCP 연결에서는 세 번의 메시지 교환을 한다.

  1. SYN: client가 연결 시작을 요청한다.
  2. SYN + ACK: server가 요청을 확인하고 자신의 연결 정보도 보낸다. ACK는 받은 내용을 확인한다는 표시다.
  3. ACK: client가 server의 정보를 확인한다.

이때 주고받는 정보에는 데이터 순서를 추적하기 위한 번호가 포함된다. 연결 준비가 되었다고 /health 요청까지 성공한 것은 아니다. HTTP 요청을 보내고 response를 받아야 앱의 처리 결과를 알 수 있다. TCP 표준

DNS·TCP·HTTP의 역할 연결하기¶

기술답하는 질문실패 예
DNS이 host 이름의 주소는 무엇인가?Could not resolve host
TCP그 주소와 port에 연결해 데이터를 주고받을 수 있는가?Connection refused
HTTP무엇을 요청했고 처리 결과는 무엇인가?404 Not Found

DNS는 주소 찾기, TCP는 연결과 데이터 전달, HTTP는 요청·응답의 의미를 담당한다. HTTP/1.1과 HTTP/2는 TCP를 사용한다. HTTP/3는 QUIC을 사용하므로 모든 HTTP가 TCP 위에서 동작하는 것은 아니다.

요청의 흐름과 세 가지 결과¶

  1. Client가 URL에서 host, port, path를 읽는다.
  2. Host가 이름이면 필요한 주소를 찾는다. 이미 저장된 결과가 있으면 재사용할 수 있다.
  3. 해당 주소와 port에 연결한다. 이번 로컬 HTTP 요청은 TCP를 사용한다. TCP는 데이터의 순서와 누락을 관리하며 프로그램 사이에 데이터를 전달하는 protocol이다.
  4. Client가 HTTP request, 즉 요청 메시지를 보낸다.
  5. Server가 path와 method에 맞는 기능을 실행하고 HTTP response, 즉 응답 메시지를 보낸다.

Method는 요청 의도를 나타낸다. 오늘 사용하는 GET은 조회다. Status code는 응답 결과를 나타내는 숫자다. URL을 잘못 썼을 때에도 어디가 틀렸는지에 따라 결과가 다르다.

상황예상 결과의미
서버 실행 + GET /health200 OK요청을 처리하고 성공 응답을 보냈다.
서버 실행 + 없는 path404 Not Found연결과 HTTP 통신은 됐지만 대상을 찾지 못했다.
서버 종료 + 같은 주소연결 실패HTTP 요청을 처리할 서버와 연결하지 못했다. HTTP status도 없다.

이 비교는 내 개발 서버에 직접 접속하는 실습 기준이다. 404는 “서버가 꺼졌다”가 아니라 응답을 받았다는 증거다.

선택 복습: 연결을 매번 새로 만들까?

기존 연결을 재사용할 수 있다. 또 HTTP/1.1과 HTTP/2는 TCP를 사용하지만 HTTP/3는 QUIC이라는 다른 전송 방식을 사용한다. 따라서 모든 HTTP 요청이 새 TCP 연결을 만드는 것은 아니다. HTTP/3 표준

실습: 같은 서버에서 결과 세 개 만들기¶

터미널 B를 추가로 연다. curl은 터미널에서 요청을 보내는 도구다. -i는 응답의 부가 정보인 header와 실제 내용인 body를 함께 보여 준다. 아래 요청은 기본 GET이다. 작은따옴표는 URL을 하나의 문자열로 전달한다.

정상 응답¶

curl -i 'http://127.0.0.1:8000/health'

출력 첫 줄의 200 OK와 빈 줄 아래 JSON을 찾는다. JSON은 데이터를 텍스트로 표현하는 형식이다. {"status":"ok"}는 status라는 항목의 값이 ok라는 뜻이다.

path만 바꾸기¶

curl -i 'http://127.0.0.1:8000/no-such-page'

예상 결과는 404 Not Found와 {"detail":"Not Found"}다. IP와 port는 그대로여서 서버에는 도착했지만, 요청을 처리할 경로가 없다.

서버 종료 후 다시 요청¶

터미널 A에서 Ctrl+C로 서버를 종료하고 종료 완료를 확인한다. 터미널 B에서 실행한다.

curl -i --connect-timeout 3 'http://127.0.0.1:8000/health'

--connect-timeout 3은 연결을 최대 3초 기다리도록 한다. 다른 서버가 같은 port를 사용하지 않는다면 보통 Failed to connect 또는 Connection refused와 curl 오류 7이 나온다. 200이나 404 같은 HTTP status가 있는지 비교한다.

막혔을 때 확인

Address already in use는 해당 port를 다른 process, 즉 실행 중인 프로그램이 사용 중일 수 있다는 뜻이다. 본인이 실행한 중복 서버를 종료하거나 서버 실행 명령과 요청 URL 모두에서 port를 8001로 바꾼다. Timeout만 보이면 그 결과를 확인한다. Timeout은 정해진 시간 안에 처리가 끝나지 않았다는 뜻이며 곧바로 404로 해석하지 않는다.

확인 질문 해설: 404면 서버에 도착한 것일까?

이번 로컬 실습에서는 그렇다. 실행 중인 앱이 없는 path에 대해 404라는 HTTP response를 보낸 것이다. 서버 종료 후 연결 실패에는 그 response 자체가 없다.

같은 개인 repository와 /health 서버를 유지한다. 다음은 2탄 — 메시지를 읽고 HTTPS 이해하기다. GET과 POST, header와 body, TLS의 역할을 작은 실습으로 연결한다.

Further More — 혼자 해보는 추가 실습¶

수업 후 선택 실습. 각자 개인 repository의 서버를 사용한다. 한 번에 한 조건만 바꾸고, 실행 전에 결과를 예상한 뒤 실제 출력과 비교한다. 아래 내용은 30분 수업 시간에 포함하지 않는다.

1. Port만 바꾸면 어떻게 될까?¶

준비: 터미널 A에서 기존 서버를 Ctrl+C로 종료한다. 다음 명령은 같은 앱을 8001에서 실행한다.

uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8001

터미널 B에서 host와 path는 같게 두고 port만 다르게 요청한다.

curl -i --connect-timeout 3 'http://127.0.0.1:8000/health'
curl -i --connect-timeout 3 'http://127.0.0.1:8001/health'

예상 결과: 다른 서버가 8000에 없다면 첫 요청은 연결 실패, 두 번째는 200이다. 8000에서도 응답이 오면 다른 서버가 켜져 있는지 확인한다. 모르는 process를 임의로 종료하지 않는다.

완료 기준: “같은 IP여도 port가 다르면 왜 결과가 다른가?”를 말로 설명한다. 끝나면 8001 서버를 종료하고 원래 명령으로 8000 서버를 다시 켠다.

2. Query와 fragment는 어디로 갈까?¶

Query는 물음표 뒤에 붙이는 추가 입력이다. week=3은 week라는 이름에 3이라는 값을 전달한다. Fragment는 # 뒤의 부분으로, 브라우저에서 문서 안 위치 등을 가리킨다. 다음 요청에서 어떤 부분이 서버에 전달될지 먼저 예상한다.

curl -v --http1.1 'http://127.0.0.1:8000/health?week=3#summary'

-v는 연결 정보와 주고받는 header를 보여 주고, --http1.1은 관찰할 HTTP 버전을 지정한다. >로 시작하는 줄은 curl이 보낸 header를 나타낸다.

예상 결과: > GET /health?week=3 HTTP/1.1에 query는 있고 #summary는 없다. 최소 서버는 query를 읽어 결과를 바꾸지 않으므로 body는 여전히 {"status":"ok"}다.

완료 기준: 실제 request line을 찾아보고 “전달된 입력”과 “서버가 활용한 입력”이 어떻게 다른지 설명한다.

3. 페이지 하나에 요청은 몇 개일까?¶

준비: 서버를 8000에서 실행하고 브라우저에서 http://127.0.0.1:8000/docs를 연다. 이 페이지는 API를 살펴보는 Swagger UI다.

  1. 브라우저 개발자 도구의 Network 탭을 연 뒤 새로고침한다. 이 탭은 페이지가 보낸 요청을 보여 준다.
  2. docs 요청을 선택하고 Headers에서 Request URL, Request Method, Status Code를 찾는다.
  3. Response에서 HTML을 찾는다. HTML은 페이지 구조를 표현하는 문서다.
  4. 추가 요청 중 두 개를 고른다. JavaScript는 페이지 동작, CSS는 모양을 담당하며 openapi.json은 API 구조를 설명하는 데이터다.

예상 결과: HTML 하나 외에도 여러 요청이 보인다. 일부는 cache, 즉 이전 결과를 저장한 곳에서 가져올 수 있다. 외부 파일이 차단되면 페이지 일부가 표시되지 않을 수 있으니 실패한 요청을 확인한다.

완료 기준: 요청 세 개의 URL·method·status를 확인하고, 한 페이지를 만드는 데 여러 요청이 필요한 이유를 설명한다. 차단된 경우에는 관찰한 요청과 차단 결과를 확인한다.
