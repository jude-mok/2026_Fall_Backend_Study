Week 04 — 백엔드에 필요한 HTTP/HTTPS 2탄

같은 서버로 시작¶

수업 전에 3주차의 실행 환경을 준비한다. 터미널 A에서 본인 repo 최상위 폴더를 열고 실행한다. 파일이 없다면 1탄의 최소 서버 준비를 먼저 완료한다. 서버 실행이 막히면 오류 메시지를 확인하고 진행자의 출력으로 관찰을 이어 간다.

uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000

Uvicorn이 연결을 받고 app/main.py의 app을 실행한다. --reload는 코드 변경 시 앱을 다시 불러온다. 실행 위치와 각 옵션은 1탄의 서버 실행 설명을 참고한다.

터미널 B에서 아래 요청을 보내 200을 확인한다. 복습 질문: “없는 path로 받은 404는 연결 실패인가?” 답은 아니다. HTTP 응답을 받은 상태다.

curl -i 'http://127.0.0.1:8000/health'

HTTP 메시지의 네 가지 부품¶

Method: 무엇을 하려는 요청인가?¶

Client는 요청을 보내는 프로그램이고, server는 요청을 받아 처리하는 프로그램이다. Method는 client가 어떤 종류의 처리를 원하는지 나타내는 단어다. 주소가 “어떤 대상인가?”를 알려 준다면 method는 “그 대상으로 무엇을 하려는가?”를 알려 준다.

예를 들어 /users를 사용자 목록, /users/7을 번호가 7인 사용자로 정했다고 하자. 이런 요청 대상인 데이터나 기능을 resource라고 부른다. 아래는 사용자 API를 그렇게 설계했을 때의 예시이며, 이번 실습에서 모두 구현하거나 실행할 필요는 없다.

Method요청의 의미사용자 API 예시
GET대상의 데이터를 조회한다.GET /users/7: 7번 사용자 정보를 읽는다.
POST데이터를 제출해 대상이 처리하도록 요청한다.POST /users: 보낸 정보로 새 사용자를 만든다.
PUT대상의 상태를 보낸 내용으로 교체한다. 없는 대상의 생성에 쓰일 수도 있다.PUT /users/7: 7번 사용자의 수정 가능한 정보를 전체 교체한다.
PATCH대상에 일부 변경을 적용한다.PATCH /users/7: 7번 사용자의 이름만 바꾼다.
DELETE대상을 삭제하도록 요청한다.DELETE /users/7: 7번 사용자를 삭제한다.
HEADGET처럼 응답 정보를 요청하되 response body는 받지 않는다.응답 상태나 형식을 내용 다운로드 없이 확인한다.
OPTIONS대상에서 가능한 통신 옵션을 요청한다.서버가 제공한다면 지원 method 등의 정보를 확인한다.

POST = 생성만은 아니다. 제출한 데이터를 처리하는 method이므로 로그인 요청 등에도 사용한다. Method 이름만으로 기능이 생기지는 않는다. 서버가 해당 요청을 처리하도록 구현되어 있어야 한다. HEAD와 OPTIONS도 앱이나 서버 설정에 따라 지원 여부가 다를 수 있다. HTTP method 참고

예시로 구분하기: PUT과 PATCH

Body는 요청에 담는 실제 내용이다. JSON은 데이터를 표현하는 형식이며, 아래 중괄호 안에는 이름과 값의 쌍이 들어 있다. name은 이름, city는 도시를 뜻한다. 이 예시 API에서는 두 항목을 수정할 수 있다고 가정한다.

변경 전: {"name":"Jude","city":"New York"}

PUT /users/7
보낼 내용: {"name":"Mok","city":"Boston"}
의도: 수정 가능한 정보를 이 내용으로 교체

PATCH /users/7
보낼 내용: {"name":"Mok"}
의도: 이름만 변경하고 도시는 유지

여기서 PATCH는 보낸 항목만 수정하도록 설계했다고 가정했다. 실제로 받는 데이터 형식과 변경 규칙은 API가 정한다. PUT에서 필수 항목을 빼면 오류가 날 수도 있으므로 “빠진 값은 무조건 유지된다”거나 “무조건 삭제된다”고 가정하지 않는다.

Endpoint: 요청이 어떤 기능으로 들어가는가?¶

API는 프로그램이 다른 프로그램의 기능을 사용하기 위한 약속이다. Endpoint는 그 기능에 접근하는 접점이다. 문서에 따라 주소 자체를 endpoint라고 부르기도 하지만, 이번 수업에서는 같은 서버 안의 method와 path를 함께 읽어 기능을 구분한다.

URL은 접근할 대상의 전체 주소이고, path는 그 주소에서 서버 안의 대상을 지정하는 부분이다. 먼저 지난주 요청을 나누어 보자.

GET http://127.0.0.1:8000/health

GET        : method — 조회 요청
http       : scheme — HTTP로 통신
127.0.0.1  : host — 내 컴퓨터
8000       : port — 서버가 요청을 기다리는 번호
/health    : path — 상태 확인 기능의 경로

이 서버에서 읽을 endpoint: GET /health

GET은 URL에 포함된 글자가 아니라 요청에 따로 지정하는 method다. 서버 주소가 다르면 같은 GET /health라도 다른 서버의 기능을 가리킨다. 또한 path는 실제 디스크의 폴더나 파일일 필요가 없다.

같은 path라도 method가 다르면 다른 기능

요청예시 API에서의 역할
GET /users사용자 목록 조회
POST /users새 사용자 생성
GET /users/77번 사용자 조회
DELETE /users/77번 사용자 삭제

앞의 두 요청은 path가 같고 method가 다르다. 첫 번째와 세 번째는 method가 같고 path가 다르다. 서버는 이런 요청을 자신에게 등록된 처리 코드와 연결한다. 이 연결 규칙을 route라고 부르고, 맞는 처리 코드를 찾는 과정을 routing이라고 부른다.

실제 코드에서는 어떻게 연결할까?

아래는 3주차의 최소 예시다. Function은 호출되면 정해진 일을 수행하는 코드 묶음이다. 여기서는 health라는 function을 요청 처리에 사용한다.

@app.get("/health")
def health():
    return {"status": "ok"}
  1. @app.get("/health")는 GET method와 /health path를 바로 아래 function에 연결한다.
  2. def health():는 health라는 function을 정의한다. URL에 쓰는 경로는 function 이름이 아니라 위에서 지정한 /health다.
  3. GET /health 요청이 들어오면 FastAPI가 연결된 function을 실행한다.
  4. return은 결과를 돌려준다. 여기서는 Python dictionary, 즉 이름과 값의 쌍을 FastAPI가 JSON response로 보내 준다.

GET만 등록한 최소 앱에서 POST /health를 보내면 이 function은 실행되지 않고 405를 받는다. /health라는 path는 있지만 POST는 지원하지 않기 때문이다. 등록되지 않은 /no-such-page를 요청하면 404를 받는다. FastAPI의 path와 operation 설명

한 단계 더: path parameter와 query parameter

Parameter는 요청마다 달라질 수 있는 입력값이다. /users/{user_id}에서 중괄호는 실제 주소에 그대로 쓰는 글자가 아니라 “이 자리에 사용자 번호가 들어간다”는 문서 표기다. /users/7이면 user_id는 7, /users/12이면 12다. 이런 값을 path parameter라고 부른다.

/users?limit=10에서 path는 /users이고, 물음표 뒤 limit=10은 query parameter다. 앱이 그렇게 구현했다면 “사용자를 최대 10명 보여 줘”라는 추가 조건이다. 보통 limit를 20으로 바꿔도 같은 목록 조회 route에 다른 입력값을 보내는 것이다. 서버가 이 값을 읽도록 구현하지 않았다면 자동으로 개수가 제한되지는 않는다.

확인 질문: 서버에 GET /health만 등록되어 있다. 같은 주소에 POST를 보내면 health function이 실행될까? 그 이유를 method와 path를 사용해서 설명해 보자.

해설 보기

실행되지 않는다. Path는 /health로 같지만 method가 POST이므로 등록된 GET /health와 일치하지 않는다. 이 최소 앱은 405 Method Not Allowed로 응답한다. 새 method를 보내는 것과 서버가 그 method를 지원하는 것은 별개의 일이다.

Header와 body: 설명과 실제 내용¶

Header는 메시지 형식 같은 부가 정보를 이름: 값으로 전달한다. Body는 실제 내용이다. 아래는 읽기용 request 예시이며, 이 사용자 생성 기능은 이번 서버에 구현하지 않는다.

POST /users HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json

{"name":"Jude"}
  • 첫 줄의 POST는 method, /users는 path, HTTP/1.1은 메시지 버전이다.
  • Host는 접속 대상이다.
  • Content-Type은 보내는 body의 형식이다. application/json은 JSON 데이터를 뜻한다.
  • Accept는 받고 싶은 응답 형식이다. 서버가 반드시 그대로 응답한다는 보장은 없다.
  • 빈 줄은 header와 body의 경계다. 그 아래 JSON은 name이라는 항목에 Jude라는 값을 담는다.

Request에 body가 항상 필요한 것은 아니다. 지난주 GET /health는 body 없이 보냈다. 서버가 JSON body를 보낼 때는 response의 Content-Type에도 application/json이 표시된다.

결과뜻이번 수업에서 연결할 상황

404 Not Found대상을 찾지 못함없는 path
405 Method Not Allowed해당 대상에서 method를 지원하지 않음GET만 등록한 /health에 POST
500 Internal Server Error서버 내부 문제로 요청을 완료하지 못함서버 코드 실행 중 처리하지 못한 오류 등

숫자는 결과를 분류하는 표지다. 200은 성공했다고 알려 주지만 현재 /health는 DB를 확인하지 않으므로 DB까지 정상이라는 증거는 아니다. 4xx나 5xx도 HTTP response이며, 연결 실패와 구분한다. Status code 참고

HTTPS는 무엇을 더할까?¶

TLS는 통신을 보호하는 protocol이다. HTTPS에서는 TLS가 HTTP 메시지를 네트워크로 보내는 구간을 보호한다. GET·POST·header·body의 의미는 그대로 사용한다.

TLS의 역할쉬운 설명
Encryption전송 내용을 암호화해서 중간에서 읽기 어렵게 한다.
Integrity전송 중 누군가 내용을 바꾸면 탐지할 수 있게 한다.
Server authentication접속한 상대가 요청한 domain의 서버인지 확인한다. 사용자 로그인을 뜻하지 않는다.

Certificate는 서버의 신원을 확인하는 데 사용하는 전자 증명서다. Client는 certificate가 접속한 host에 맞고, 유효하며, 신뢰할 수 있는 발급 체계로 이어지는지 등을 검사한다. 연결을 시작하며 통신 조건을 맞추고 상대를 확인하는 절차를 TLS handshake라고 한다.

새 HTTPS 연결의 개념 흐름 (HTTP/1.1 예)
서버에 연결 → TLS handshake → 보호된 HTTP request/response

HTTPS는 서버가 받은 뒤 데이터를 잘못 저장하거나, 다른 사용자에게 보여 주는 앱 오류까지 해결하지 않는다. 개발자 도구에서 JSON이 보이는 것은 정상이다. 브라우저는 통신의 끝점이므로 받은 데이터를 해독해 보여 준다. TLS 공식 설명

로컬 실습의 http://127.0.0.1:8000은 HTTP 서버다. 주소 앞부분만 https로 바꿔도 HTTPS 서버가 되지 않는다. 서버 또는 앞단의 호스팅 서비스에서 TLS 설정이 필요하다. 오늘은 공개 HTTPS 서버를 관찰한다.

실습 A: URL은 같고 method만 다르게¶

터미널 B에서 순서대로 실행한다. -i는 response header와 body를 보여 준다. -X POST는 method를 POST로 지정한다.

curl -i 'http://127.0.0.1:8000/health'
curl -i -X POST 'http://127.0.0.1:8000/health'

예상: 3주차 최소 서버라면 첫 요청은 200과 {"status":"ok"}, 두 번째는 405와 {"detail":"Method Not Allowed"}다. 두 번째 response의 Allow: GET은 이 대상에서 허용하는 method를 알려 준다. Header 대소문자와 순서는 달라질 수 있다.

  1. 각 출력에서 status line, Content-Type, 빈 줄 아래 body를 표시한다.
  2. “/health가 없어서 405인가?”에 답한다. Path는 있지만 POST를 지원하지 않는 것이다.
  3. 이미 본인 앱에 POST /health를 추가했다면 405가 아닐 수 있다. 실제 결과를 확인하고 어떤 method를 등록했는지 확인한다.

완료 기준: GET과 POST의 결과를 비교하고, 404와 405의 차이를 한 문장으로 설명한다. 이번 실습에서는 POST를 처리할 코드를 추가하지 않는다.

실습 B: HTTPS 연결을 눈으로 확인¶

외부 Internet 연결이 필요하다. -v는 연결 과정과 주고받은 header를 자세히 보여 주고, --http1.1은 예제와 같은 HTTP 버전을 사용한다. --connect-timeout 3은 연결 단계, --max-time 8은 전체 작업의 대기 시간을 제한한다.

curl -v --http1.1 --connect-timeout 3 --max-time 8 'https://example.com/'

출력에서 다음 세 가지를 찾는다. 문구와 줄 순서는 curl 버전 및 환경마다 다르다.

찾을 증거출력에 나타날 수 있는 단어읽는 법
TLS 연결SSL connection / TLS보호된 연결을 사용한다. 일부 도구는 TLS 정보에 SSL이라는 이름을 쓴다.
Certificate 확인certificate / verify서버 certificate와 검증 결과에 관련된 정보다.
HTTP 메시지> GET / HTTP/1.1
< HTTP/1.1 …		>는 보낸 header, <는 받은 header 표시다. 표시 자체는 HTTP에 포함되지 않는다.

완료 기준: 실제 출력에서 TLS 관련 줄 하나와 HTTP 응답 줄 하나를 찾는다. Certificate 정보가 있으면 함께 표시한다. 예시 단어가 반드시 그대로 나와야 하는 것은 아니다.

Network 차단이나 certificate 오류로 실패하면 재시도에 시간을 쓰지 않고 실패한 단계와 실제 메시지를 확인한다. 아래 흐름 예시를 함께 읽고 직접 관찰한 결과와 예시를 구분한다. Certificate 검증을 끄는 옵션으로 우회하지 않는다.

관찰 대체용 예시 · 실제 실행 기록과 구분
TLS 연결 정보
server certificate 검증 결과
> GET / HTTP/1.1
> Host: example.com
< HTTP/1.1 200 OK
< Content-Type: text/html

실제 출력의 순서를 설명하기 위한 요약이다. HTTPS여도 연결의 끝점인 curl은 HTTP header와 body를 읽을 수 있다. 이것은 전송 중 데이터가 평문이라는 뜻이 아니다. Proxy를 쓰는 환경에서는 proxy 연결 정보도 함께 보일 수 있다.

자기 설명 해설

Content-Type과 Accept: 전자는 내가 보내는 body의 형식, 후자는 받고 싶은 형식이다. 404와 405: 이번 앱에서는 없는 path와 지원하지 않는 method의 차이다. HTTPS와 권한: TLS는 통신 구간을 보호하지만 사용자가 다른 사람의 데이터를 봐도 되는지는 앱이 판단해야 한다.

선택 복습과 다음 연결¶

더 확인할 때는 HTTP method, status code, TLS, curl 옵션을 참고한다. 다음 5주차 REST API에서는 이 부품으로 사용자 API의 요청과 응답을 설계한다.

Further More — 혼자 해보는 추가 실습¶

수업 후 선택 실습. 개인 repository의 기존 서버를 사용한다. HTTP 메시지를 더 자세히 읽고, HTTPS 연결의 끝점에서 무엇을 볼 수 있는지 확인한다. 30분 수업과 별도로 진행한다.

1. Accept를 바꾸면 응답도 바뀔까?¶

준비: /health 서버를 8000에서 실행한다. -H는 request에 header를 추가하는 curl 옵션이다. 아래 두 명령은 받고 싶은 형식인 Accept만 바꾼다. text/plain은 일반 텍스트 형식을 뜻한다.

curl -v --http1.1 -H 'Accept: application/json' 'http://127.0.0.1:8000/health'
curl -v --http1.1 -H 'Accept: text/plain' 'http://127.0.0.1:8000/health'

예상 결과: 위 최소 서버는 두 요청에 모두 200과 JSON을 반환한다. 이 앱에는 Accept에 따라 응답 형식을 선택하는 코드가 없다. Client의 희망을 전달하는 것과 server가 그 희망을 처리하는 것은 다르다.

완료 기준: 보낸 > Accept:, 받은 < content-type:, body를 두 요청에서 비교한다. “Accept를 text/plain으로 쓰면 JSON이 자동으로 일반 텍스트로 바뀐다”가 왜 틀린지 설명한다.

2. HTTP 404와 curl의 종료 상태 비교¶

Exit code는 명령이 끝날 때 운영체제에 돌려주는 결과 숫자다. 보통 0은 명령 성공, 0 이외의 값은 문제를 나타낸다. HTTP status code와는 다른 값이다. macOS의 zsh 또는 bash 터미널에서 각 curl 직후 echo $?를 실행하면 바로 이전 명령의 exit code를 볼 수 있다.

curl -i 'http://127.0.0.1:8000/no-such-page'
echo $?
curl --fail-with-body -i 'http://127.0.0.1:8000/no-such-page'
echo $?

--fail-with-body는 HTTP 오류 응답을 받으면 curl도 실패로 끝내되 body는 보여 주는 옵션이다. 구버전 curl에서 지원하지 않으면 두 번째 비교는 생략하고 지원하지 않는다는 메시지를 확인한다.

예상 결과: 정상 실행 중인 최소 서버에서는 둘 다 HTTP 404다. 첫 명령의 exit code는 0, 두 번째는 22다. 첫 번째 curl은 “404 응답을 정상적으로 받는 일”에 성공했기 때문이다. 중간에 다른 명령을 실행하면 $?의 대상도 바뀐다.

완료 기준: HTTP status와 exit code를 각각 확인하고, 자동화에서 HTTP 오류도 실패로 처리하려면 왜 옵션이 필요한지 설명한다.

3. Certificate와 HTTPS 응답을 브라우저에서 확인¶

준비: 브라우저에서 https://example.com/을 연다. 개인정보나 로그인 없이 관찰할 수 있는 페이지다.

  1. 주소창의 사이트 정보 메뉴에서 연결 보안과 certificate 정보를 찾는다. 브라우저에 따라 메뉴 이름과 위치는 다르다.
  2. Certificate의 대상 host 이름, issuer, 유효기간을 확인한다. Issuer는 certificate를 발급한 주체이며, 유효기간은 언제부터 언제까지 사용할 수 있는지 나타낸다. 대상 이름은 Subject Alternative Name 항목 등에 표시될 수 있다.
  3. 개발자 도구의 Network 탭을 연 뒤 새로고침한다. 문서 요청의 URL이 https인지 확인하고 response status와 Content-Type을 확인한다.
  4. Response에서 HTML 내용이 보이는지 확인한다. HTML은 브라우저가 페이지를 그리는 데 쓰는 문서다.

예상 결과: 유효한 HTTPS 연결이라면 certificate 정보와 HTTP response를 확인할 수 있다. Certificate의 발급자와 날짜, 응답 header는 갱신될 수 있으므로 직접 표시된 값을 확인한다. Network나 보안 정책으로 접속이 막히면 그 결과를 확인한다.

완료 기준: certificate 정보와 response를 확인하고 “HTTPS인데 왜 Response 탭에서 내용이 보이는가?”에 답한다.

해설: HTTPS인데 내용을 볼 수 있는 이유

브라우저는 TLS 연결의 끝점이어서 받은 데이터를 해독한다. 개발자 도구는 이 해독된 내용을 보여 준다. 전송 중 중간에서 읽을 수 있다는 뜻은 아니다. Certificate로 서버를 확인하는 과정과, 앱에서 사용자의 데이터 접근 권한을 확인하는 과정도 서로 다르다.
